## 一、bootloop：先分清「崩溃」还是「躺平」

> 原标题：**启动循环（bootloop）类问题排查方法论**，已并入本文

> 适用场景：**串口只有 ROM 引导码、App 一行输出都没有、设备在反复重启**。
> 本文以本次「16MB 分区表 → bootloader 死循环」为例，沉淀一套**可复用的定位流程**。
> 结论本身写在 `01-板级硬事实与构建烧录.md` 的 1.4 节，本文讲**怎么查出来的**。

---

### 0. 先分清"崩溃"和"躺平"——这一步决定排查方向

**bootloop 不等于崩溃。** 两类完全不同的机制，症状却很像：

| | 异常崩溃 | 主动死循环（本次） |
|---|---|---|
| 复位原因 | `rst:0x8/0x9` 或 Guru Meditation | **`rst:0x3 (RTC_SW_SYS_RST)`** |
| 串口 | 有 panic / backtrace / abort | **完全没有错误输出** |
| `Saved PC` | 每次可能不同 | **恒定不变** |
| 本质 | CPU 踩到非法操作 | 代码**故意** `while(1)`，靠 **RTC 看门狗**复位 |

判断口诀：**看到 `rst:0x3` + 零错误输出 + `Saved PC` 恒定 → 九成是死循环等看门狗**，
此时去反汇编那个 `Saved PC` 是最快的路，而不是去查崩溃栈。

---

### 1. 反汇编 bootloader 崩点（关键证据）

`Saved PC:0x403cd9aa` 落在 RTC/IRAM 段内 → 属于**二级 bootloader**，不是 App。
（对照 `firmware.bin` 的 IRAM 段范围即可确认归属。）

#### 1.1 两个必踩的坑

1. **`bootloader.bin` 是 ESP image，开头是 header（魔数 `E9`）不是代码**。
   直接 `objcopy -I binary` 整个文件反汇编，开头必然解出乱码。
2. **段是按加载地址重定位的，不是线性连续的**。
   直接用 `--adjust-vma <首段地址>` 做线性映射，目标地址会落到错误位置。

#### 1.2 正确做法：先解析 image，抽出崩点所在段，再按该段加载地址反汇编

```python
# 1) 解析 ESP image header（8 字节主头 + 16 字节扩展头）
segs = b[1]; off = 24
for i in range(segs):
    addr, ln = struct.unpack('<II', b[off:off+8])
    data = b[off+8:off+8+ln]
    if addr <= CRASH < addr + ln:      # 崩点落在该段
        open('seg.bin','wb').write(data)
        # 2) 用该段自己的加载地址做 vma
        objcopy -I binary -O elf32-xtensa-le -B xtensa \
                --adjust-vma <addr> \
                --rename-section .data=.text \
                --set-section-flags .text=alloc,load,readonly,code \
                seg.bin seg.elf
        objdump -D -m xtensa seg.elf
```

工具路径：`~/.platformio/packages/toolchain-xtensa-esp32s3/bin/`（`objcopy` / `objdump` / `addr2line`）。

> ⚠️ 直接对 raw binary 跑 `objdump -b binary -m xtensa` 会**访问越界崩溃**（RC=0xC0000005）。
> 必须先转 ELF。另外 `.data` 段必须改名成 `.text` 且标记 code，否则解出来是数据。

本次解出的关键指令：

```
403cd9aa:  j  403cd9aa      ← 跳自己，死循环实锤
```

### 2. 二分法：用极简工程判定"配置问题" vs "App 问题"

**这是本次效率最高的一步。** 当怀疑构建配置时，别在主工程上反复试——
主工程编译慢、变量多、还混着自己的代码问题。

建一个独立极简工程（`tools/minimal_test/`），**复用完全相同的板级配置**，
`main.cpp` 只做 `Serial.println`：

```cpp
void setup(){ Serial.begin(115200); delay(500); Serial.println("[MIN] boot ok"); }
void loop (){ Serial.println("[MIN] alive"); delay(1000); }
```

然后：

- 极简工程**也**死循环 → **配置/构建问题**，App 代码清白 ✅（本次结论）
- 极简工程能启动 → 问题在自己 App 侧

极简工程编译快（十几秒），适合**逐项扫描配置**：
本次依次验证 `无PSRAM`、`8MB默认分区`、`8MB+OPI PSRAM`，
最后一组 **`reset count: 0`** 完美启动，直接锁定元凶是 16MB 那两行配置。

> 循环打印（每秒一条）比只打印一次更好用：串口晚开几秒也抓得到。

---

### 3. 镜像体检：先确认"文件没坏"，再怀疑别的

用 esptool 给两个镜像做体检，能一次性排除大量猜测：

```bash
python -m esptool --chip esp32s3 image_info .wb_build/esp32s3/firmware.bin
python -m esptool --chip esp32s3 image_info .wb_build/esp32s3/bootloader.bin
```

本次报告：`Checksum: valid`、`Validation hash: valid`、段地址合法、`App version: esp-idf v4.4.7`
→ **镜像本身没问题**，于是排除"固件损坏"、"hash 校验失败"等方向。

顺带 `esptool erase_flash` 还会做一次**硬件体检**，本次输出：

```
Chip type: ESP32-S3 (QFN56) (revision v0.2)
Features: Wi-Fi, BT 5, Dual Core, 240MHz, Embedded PSRAM 8MB (AP_3v3)
```

看到 `Embedded PSRAM 8MB` 即可确认 **PSRAM 硬件正常**，彻底排除硬件损坏。

### 4. 本次被逐一证否的假设（避免重复踩）

排查过程中以下假设**全部被实测推翻**，记录下来省得下次再走：

| 假设 | 推翻依据 |
|---|---|
| bootloader 把 flash 切成 QIO 了 | `bootloader.bin` header 自身是 `flash_mode=DIO` |
| `flash_size=0x0F` 非法导致失败 | 用 `--flash_size 16MB` 重新生成，该字段**仍是 `0x0F`** → 它是 esptool 的正常特殊编码 |
| PSRAM 初始化失败 | 去掉 `qio_opi` / `-DBOARD_HAS_PSRAM` 后**照样**死循环 |
| `sdkconfig.defaults` 能改 bootloader 配置 | Arduino 框架下 `.wb_build` **不生成 `sdkconfig`**，该文件根本没被采纳 |
| `build_flags -DCONFIG_SPIRAM_*` 能传给 bootloader | bootloader 走独立子项目，崩溃地址**分毫未变** |
| otadata / NVS 残留导致找不到 App | `erase_flash` 全片擦除后重烧，**依然**死循环 |
| 是我们浏览器/LVGL 代码的问题 | 极简工程同样死循环 |

---

### 5. 环境层面的坑（会严重拖慢排查）

#### 5.1 bash shim 坏了，别信它的退出码

`ls` / `cd` / `dirname` / `head` / `grep` 常报 `command not found`。
**`rc=127` 是 shim 本身失败，不代表你的命令失败**——本次就出现过
"日志显示编译成功、退出码却是 127"的假失败。

对策：
- 输出一律**重定向到文件再读**，不要用 `| head` / `| grep`。
- 长任务（编译/烧录）**写一个 Python 驱动脚本**用 `subprocess` 调用，
  把 stdout 写进日志文件、把真正返回码写 stderr。比 shell 可靠得多：
  `tools/build_run.py`、`tools/flash_run.py`、`tools/minimal_run.py`。

#### 5.2 串口日志含二进制字节

直接用 Read 打开会被判为二进制文件。
用 Python 以 `errors='ignore'` 解码后再筛选，并**过滤掉 ROM 引导码**：

```python
bootrom = ("ESP-ROM","rst:0x","boot:0x","Saved PC","SPIWP",
           "mode:DIO","load:0x","entry 0x","ets Jun","Build:Mar")
```

#### 5.3 抓启动横幅要复位后立刻抓

主工程不像极简工程那样循环打印，启动横幅一闪而过，
直接开串口常常只能抓到空白（但 `reset count: 0` 已能说明没重启循环）。
用 `tools/reset_capture.py`（**拉 RTS/DTR 复位后立刻读 20s**）才抓得到
`[BOOT] Geek Terminal ready`。

---

### 6. 一句话总结

> **看到 `rst:0x3` + 无 panic + `Saved PC` 恒定 → 反汇编那个 PC；
> 看到 `j <自己>` → 就是 fatal 死循环；
> 然后用极简工程二分，区分"配置问题"和"App 问题"。**

## 二、实战：谁删了我的屏（悬空指针）

> 原标题：**11 · "谁删了我的屏"：auto_del 与常驻 lv_timer 的悬空指针**，已并入本文

> 现象：浏览器渲染刚成功（`widgets created: 39`、`contentH=730`），下一秒
> `Guru Meditation Error: Core 1 panic'ed (LoadProhibited)` 重启。
> 影响面：**任何在 3 秒内就切进非 Launcher 应用的路径都会崩**（串口 `nav` / `browser`、
> 开机立刻触摸）。不只是浏览器。

---

### 1. 崩溃现场

```
[Browser] render done. visible=414 scrollable=318 total=732
[Browser] g_urlArea=0x3fca53d8 valid=1 nav_browser=0x3fca37f8
[App] screen changed: 0x3fca37f8 -> 0x3fca29a8, nav_browser=0x3fca37f8 valid=1
Guru Meditation Error: Core  1 panic'ed (LoadProhibited).
EXCVADDR: 0xf501e41f  EXCCAUSE: 0x0000001c
Backtrace: 0x420e32ff 0x420204f8 0x4202eb75 0x42006b79 0x4202ace0 0x42001faa ...
```

两个可疑点：**活跃屏被换成了 Launcher**（`0x3fca29a8`，对比重启后日志
`0x3fca4708 -> 0x3fca29a8` 可确认它是 `nav_launcher`），而且 **nav.cpp 没有打印
任何 `[Nav] release`** —— 也就是说浏览器屏不是被 `nav_release_all_except()` 删的。

### 2. 定位：addr2line

```bash
python tools/a2l.py 0x420e32ff 0x420204f8 0x4202eb75 0x42006b79 ...
```

```
0x420e32ff  _lv_obj_get_ext_draw_size   lv_obj_draw.c:372
0x420204f8  lv_obj_invalidate           lv_obj_pos.c:818
0x4202eb75  lv_label_set_text           lv_label.c:90
0x42006b79  update_cb(lv_timer_t*)      src/app/status_bar.cpp:69   ← 我们的代码
0x4202ace0  lv_timer_exec / lv_timer_handler
0x42001faa  App::loop()                 src/app/app.cpp:143
```

`EXCVADDR = A8 + 0x16`，而 `A8 = 0xf501e409` —— 一个既不在 DRAM 也不在 PSRAM 的
野地址（0x3fcxxxxx / 0x3dxxxxxx 才是合法区）。`lv_obj_draw.c:372` 是
`obj->spec_attr` 的解引用，所以 **`lv_label_set_text()` 拿到的是已释放的 label**。

结论：崩的是状态栏的 1s 定时器，不是浏览器。浏览器只是倒霉的受害者。

### 3. 根因：欢迎屏 3 秒定时器 + auto_del

`src/app/welcome.cpp`：

```c
g_timer = lv_timer_create(timer_cb, 3000, nullptr);   // 3s 后进主桌面

void enterLauncher() {
  ...
  lv_scr_load_anim(nav_launcher, LV_SCR_LOAD_ANIM_MOVE_BOTTOM, 500, 0, true);
  //                                                               ^^^^ auto_del
}
```

`lv_scr_load_anim(..., auto_del=true)` 删的是**被替换掉的旧屏**，不是欢迎屏。
3 秒内用户已经切到浏览器 → 旧屏就是浏览器屏 → 它被静默 `lv_obj_del()` 掉：

1. `nav_browser` 仍指向已释放内存（`nav.cpp` 无从得知，所以没有 release 日志）；
2. 屏上的 `lv_timer` **不属于对象树**，`lv_obj_del()` 不会带走它 —— 状态栏那个
   1s 定时器继续跑，下一拍写到已释放 label → LoadProhibited。

雪上加霜的是状态栏自己还有第二个 bug：`StatusBar_create()` 每被调用一次就
`lv_timer_create()` 一个，且所有定时器共用同一组 `g_fpsLabel/...` 全局指针。
Launcher + Browser = 2 个定时器抢同一组指针。

### 4. 修复

**welcome.cpp —— 定时器不许抢屏，auto_del 只许删自己**

```c
const bool autoDel = (g_scr != nullptr && lv_scr_act() == g_scr);
lv_scr_load_anim(nav_launcher, LV_SCR_LOAD_ANIM_MOVE_BOTTOM, 500, 0, autoDel);

void timer_cb(lv_timer_t* t) {
  if (!g_scr || lv_scr_act() != g_scr) {   // 已经不在欢迎屏 → 放弃
    if (g_timer) { lv_timer_del(g_timer); g_timer = nullptr; }
    g_entered = true;
    return;
  }
  enterLauncher();
}
```

**status_bar.cpp —— 单组全局指针 → bar 注册表；定时器全局只建一次**

- `Bar s_bars[MAX_BARS]`（含 `wifiLevel` 各自独立），`allocBar()` 取空槽；
- `lv_obj_add_event_cb(bar, bar_delete_cb, LV_EVENT_DELETE, nullptr)`：
  屏被删（不管谁删的）→ 立刻清空槽位；
- `update_cb()` 遍历槽位，每个控件写之前 `lv_obj_is_valid()` 验活；
- `lv_timer_create()` 只在首次调用时执行一次。

### 5. 验证

烧录后 `python tools/cap_url.py 100 "https://m.baidu.com/" 50`：

```
[Browser] render done. visible=414 scrollable=318 total=732
[Browser] g_urlArea=0x3fca542c valid=1 nav_browser=0x3fca384c
>>> sent: mem                       ← 距渲染完成 50s，中途再无 screen changed
[Console] DRAM(internal) free: 25512, PSRAM free: 7448555
```

渲染后 **50 秒**停留浏览器屏、无 panic —— 对比修复前 3 秒必崩。

### 6. 通用教训（下次照抄）

| 规则 | 说明 |
|---|---|
| `lv_timer` 不属于对象树 | `lv_obj_del()` 屏不会带走挂在它上面的定时器。凡持有对象指针的定时器，必须自己登记注销（`LV_EVENT_DELETE`）或每拍验活 |
| 别用单组全局指针存控件 | 两条 bar / 两个屏就是两套生命周期。用注册表 + 槽位 |
| `auto_del=true` 是隐式 delete | 它删的是"当时活跃的那个屏"，可能根本不是你想删的屏。只在确认 `lv_scr_act() == 自己的屏` 时才传 true |
| 启动类一次性定时器要自检 | "3 秒后做 X" 必须先看"现在还该我做吗" |
| 崩在 LVGL 里 ≠ LVGL 的错 | `addr2line` 找到第一个属于 `src/` 的帧（`0x42006b79`），那里才是真凶 |

### 7. 排障工具

- `tools/a2l.py <addr>...`：批量 addr2line（自动找 `.wb_build/esp32s3/firmware.elf`）。
- `tools/cap_url.py <秒数> <url> [渲染后等待秒数]`：开浏览器加载并在渲染后继续观察，
  专治"渲染完过一会儿才崩"。
- 定位"这个地址是哪个屏"：拿重启后日志里的 `screen changed` 序列做对照，
  LVGL 对象地址在同一个启动流程下是稳定的。
