## 一、两阶段异步架构与 Lexbor CSS 崩溃修复

> 原标题：**浏览器异步架构与 Lexbor CSS 崩溃修复**，已并入本文

### 背景

在 ESP32-S3（16MB Flash / 8MB OPI PSRAM / 480×480 RGB IPS）上实现 TactileBrowser 引擎，
加载百度首页（~729KB HTML + 26KB CSS + 407B CSS）。核心挑战：
1. LVGL 不是线程安全的，所有 UI 操作必须在同一任务中
2. Lexbor CSS 解析器在解析大 CSS 后内部状态破坏，后续调用崩溃
3. ESP32-S3 双核任务调度 + PSRAM 带宽争抢

### 一、两阶段异步架构

#### 问题
后台任务下载+解析+渲染全做 → 后台任务调 LVGL → Core 1 `lv_scr_load_anim` 崩溃

#### 解决方案
将浏览器加载拆分为两个阶段：

| 阶段 | 执行核 | 任务 | 涉及 LVGL |
|------|--------|------|-----------|
| Phase 1 | Core 0 (后台任务) | 下载 HTML + 解析 DOM + 构建布局树 | 否 |
| Phase 2 | Core 1 (UI 任务) | 创建 LVGL 控件 + 渲染 | 是 |

#### 关键实现

**状态机**：`BROWSER_IDLE → BROWSER_LOADING → BROWSER_LOADED / BROWSER_STOPPED / BROWSER_ERROR`

**后台任务**（`fetch_task`, Core 0, 64KB 栈）：
```cpp
g_taskResult = tactilebrowser_download_and_parse(
    url, 460, 360, &g_stopRequested, &g_layoutRoot);
g_taskDone = true;  // 通知 UI 任务
```

**UI 任务**（`BrowserScreen_tick`）检查 `g_taskDone` → 调用 Phase 2 渲染。

**引擎重建在 UI 任务中做**（不在后台任务中）：
```cpp
void startFetch(const String& url) {
    ensureEngineInit();
    // 引擎重建在 UI 任务中，避免后台任务操作全局状态
    tactilebrowser_core_cleanup();
    tactilebrowser_core_init();
    tactilebrowser_set_renderer(&g_renderer->base);
    tactilebrowser_set_html_downloader(arduino_download_html);
    // 创建后台任务
    xTaskCreatePinnedToCore(fetch_task, "fetch", 65536, NULL, 1, &g_fetchTask, 0);
}
```

#### 协作式停止
`volatile bool g_stopRequested`，下载循环和 DOM 遍历每块检查。
用户点"停止"按钮 → `g_stopRequested = true` → 后台任务退出。

#### 加载遮罩
半透明黑色 + "加载中，请稍等..." + 进度条 + 大红色停止按钮。

### 二、Lexbor CSS 解析器崩溃修复

#### 现象
解析百度 26KB CSS 后，后续调用 `lxb_css_declaration_list_parse` 解析颜色值时崩溃：
```
EXCVADDR=0x08 (NULL+8)
backtrace: lxb_css_syntax_parse_declarations → lxb_css_declaration_list_parse
          → css_parser_parse_color_value (css_parser.cpp:521)
          → layout_apply_css_property → build_layout_tree_from_dom
```

#### 根因
Lexbor CSS 解析器有**内部全局状态**。解析大 CSS（26KB）后内部状态破坏，
后续任何 `lxb_css_declaration_list_parse` 调用都会访问已破坏的内存。

#### 解决方案：完全移除 Lexbor CSS 回退

`css_parser_parse_color_value` 只用手动解析，不依赖 Lexbor：

```cpp
bool css_parser_parse_color_value(const char *value, uint32_t *color_out) {
    if (!value || !color_out) return false;
    // 只用手动解析，完全不依赖 Lexbor CSS 解析器
    return parse_color_manual(value, color_out);
}
```

`parse_color_manual` 支持的格式：
- `#RGB` / `#RRGGBB`
- `rgb(r, g, b)` / `rgba(r, g, b, a)`（忽略 alpha）
- 常见颜色名（black/white/red/green/blue/...共 20 种）

解析失败 → 返回 false（颜色不应用，但不崩溃）。

#### 为什么不修复 Lexbor 本身？
1. Lexbor 是第三方库，内部状态管理复杂
2. 裁剪版已去掉 selectors/style/unicode 等模块，可能引入了不一致
3. 手动解析覆盖 95%+ 的实际颜色值，足够用
4. 即使修复了颜色解析，其他 Lexbor CSS 调用也可能崩溃

### 三、ESP32-S3 双核协作要点

#### 核心分配
- **Core 0**：WiFi/BT 任务、后台下载/解析任务
- **Core 1**：Arduino `loop()`、LVGL `lv_timer_handler()`、UI 渲染

#### 让双核合作的关键
- `vTaskDelay(1)` 在下载循环、DOM 遍历每 50 节点、渲染每 30 节点调用
- 让 Core 0 WiFi 任务喘气，避免看门狗超时

#### 内存注意事项
- `ESP.getFreeHeap()` 在 ESP32-S3 上会锁多堆，阻塞 CPU1 WiFi 任务 → 用 `xPortGetFreeHeapSize()`
- Lexbor 内存重定向到 PSRAM（`lexbor_memory_setup()`）
- Lexbor 完整版 DRAM 溢出 → 裁剪 selectors/style/unicode/punycode/engine/url 六个模块

### 四、CSS 限制

| 类型 | 限制 | 说明 |
|------|------|------|
| 外部 CSS | 64KB | 百度 26KB CSS 可完整解析 |
| 内联 CSS | 32KB | style 属性 |
| HTML 缓冲 | 768KB | 百度 729KB HTML 可完整读取 |

### 五、验证结果

百度首页加载成功：
- HTML: 729KB (status=200)
- CSS: 26KB + 407B (两个外部 CSS)
- 106 个 LVGL widget 创建
- 无崩溃、无看门狗超时
- 加载完成后可滚动浏览

### 六、经验总结

1. **LVGL 不是线程安全的**：所有 LVGL 操作必须在同一个任务中。后台任务只做数据准备，UI 任务做渲染。
2. **第三方库的内部状态**：Lexbor CSS 解析器有内部全局状态，大输入可能破坏状态。如果只需要简单解析（如颜色值），手动解析比依赖库更安全。
3. **双核协作**：`vTaskDelay(1)` 是让双核合作的关键。长时间运行的任务必须定期让出 CPU。
4. **引擎重建时机**：有状态的全局引擎重建必须在 UI 任务中做，不能在后台任务中做（会破坏正在使用的全局状态）。
5. **PSRAM 内存重定向**：大缓冲区（HTML 768KB、Lexbor 内存）重定向到 PSRAM，避免 DRAM 溢出。

### 1. 问题：`Failed to create fetch task!`

#### 1.1 现象

串口触发网页加载：

```
[Browser] DRAM free: 94936, PSRAM free: 6602431
[Browser] Failed to create fetch task!
```

不崩溃、不重启，就是加载不出来。**重复点击多少次都没用**。

#### 1.2 根因：内部 DRAM 耗尽 + 碎片

FreeRTOS 任务栈**只能从内部 DRAM 分配**，PSRAM 帮不上忙。当时：

| 指标 | 值 |
|---|---|
| 内部 DRAM 空闲 | **~93 KB** |
| 后台任务栈需求 | 48 KB **连续**块 |
| 结果 | 碎片堆里凑不出连续 48KB → 创建失败 |

第一次加载能成功，是因为**启动早期 DRAM 更充足**；跑到第二次就永远失败。

> ⚠️ **排障陷阱**：`serial_console` 的 `mem` 命令用 `xPortGetFreeHeapSize()`，返回的是**含 PSRAM 的总堆**，
> 会显示 6.8MB，看起来"内存很够"。真实内部 DRAM 要看
> `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`。两者差 **70 倍**。
> 现已修正 `cmdMem()`，分别打印 DRAM / PSRAM / total heap / 最大连续块。

#### 1.3 DRAM 被谁吃了

ESP32 没有 MMU、没有虚拟内存、没有换页。`lv_obj_create(NULL)` 建的每个屏幕都是
一棵**常驻**的 LVGL 对象树，不显式 `lv_obj_del()` 就永远占着。
启动时一次性创建了 **10 个屏**：

```cpp
nav_clock    = ClockScreen_create();
nav_settings = SettingsScreen_create();
nav_wifi     = WifiScreen_create();
nav_game     = GameScreen_create();
nav_browser  = BrowserScreen_create();
nav_draw     = DrawScreen_create();
nav_memory   = MemoryScreen_create();
nav_sysinfo  = SysInfoScreen_create();
nav_weather  = WeatherScreen_create();
nav_launcher = LauncherScreen_create();
```

### 2. 修复一：后台 fetch 任务改为启动时常驻

**关键洞察**：既然运行时凑不出 48KB 连续栈，那就**在 DRAM 最充足、还没碎片的时候一次性申请，之后永不释放**。

改法：

| 之前 | 之后 |
|---|---|
| 每次加载 `xTaskCreatePinnedToCore` 现创任务 | 启动时 `BrowserScreen_preinit()` 建一次，**常驻** |
| 干完活 `vTaskDelete(NULL)` | 干完活回到 `ulTaskNotifyTake()` 等待，不删除 |
| 反复申请/释放 48KB → 碎片 | 零碎片，零失败 |
| `g_fetchTask` 变成失效句柄 | 句柄永远有效 |

```cpp
void fetch_task(void* param) {
  for (;;) {
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);   // 等待 UI 通知
    if (g_stopRequested) { g_taskDone = true; continue; }
    g_taskResult = tactilebrowser_download_and_parse(
        g_fetchUrl.c_str(), 460, 360, &g_stopRequested, &g_layoutRoot);
    g_taskDone = true;
  }
}
```

启动时调用（在**任何屏幕创建之前**，DRAM 最充足）：

```cpp
BrowserScreen_preinit();   // App::begin() 中，第 7 步之前
```

#### 顺带修掉一个死等 bug

原 `startFetch()`：

```cpp
if (g_fetchTask != nullptr) {
  g_stopRequested = true;
  for (int i = 0; i < 200 && g_fetchTask != nullptr; i++)
    vTaskDelay(pdMS_TO_TICKS(10));   // 白等 2 秒
}
```

`g_fetchTask` 只在 `BrowserScreen_tick()` 里被清空，而 **tick 和 startFetch 同在 UI 任务**——
阻塞期间 tick 根本跑不到，条件永远不成立。改为**非阻塞排队**：

```cpp
if (g_state == BROWSER_LOADING) {
  g_stopRequested = true;
  g_pendingUrl = url;  g_hasPending = true;   // 排队，tick 收尾后续上
  return;
}
```

### 3. 修复二：Activity 注册表（按需创建 / 退出即毁）

新增 `src/app/nav.cpp`，把每个应用登记成一條记录：

```cpp
struct ActivityEntry {
  const char* name;
  lv_obj_t**  screen;      // 指向全局指针（如 &nav_clock）
  Creator     create;      // 按需创建
  CanRelease  canRelease;  // 释放守卫（nullptr = 总是可释放）
};
```

API：

| 函数 | 作用 |
|---|---|
| `nav_open(&nav_xxx)` | 指针为空则创建并回写；否则直接返回 |
| `nav_release_all_except(a, b)` | 销毁除 a/b 外所有已加载 Activity，`lv_obj_del` + 指针置 `nullptr` |

规则：

- **Launcher 常驻**（轻量，是返回锚点）
- 其余应用 **进入时创建、抢占/离开时销毁**
- 同一时刻最多 **2 棵对象树**存活

#### 释放守卫（安全性）

`App::loop()` 里 WiFi 屏被独立 tick：

```cpp
if (act == nav_wifi || WifiScreen_isConnecting()) WifiScreen_tick();
```

若正在连接时把屏销毁，tick 会打到悬空指针上。**双重保险**：

1. `app.cpp`：`if (nav_wifi && (act == nav_wifi || WifiScreen_isConnecting()))`
2. 注册表给 wifi 配 `canRelease = []{ return !WifiScreen_isConnecting(); }`

### 5. 修复四：退出时真释放 + URL 栏降级

#### 5.1 `BrowserScreen_close()`

退出不再只是切屏（原来如此，内存全留着）：

```cpp
void BrowserScreen_close() {
  g_stopRequested = true;                    // 后台任务尽快收手（常驻，不删除）
  if (g_content) lv_obj_clean(g_content);    // 释放数十个网页 widget（大头）
  if (g_layoutRoot) { tactilebrowser_free_layout(g_layoutRoot); g_layoutRoot = nullptr; }
  hideLoadingOverlay();
  g_state = BROWSER_IDLE;
}
```

**屏壳（顶栏/底栏少量控件）保留**——避免下次进入重建开销，也避免静态控件指针悬空。

#### 5.2 URL 栏：`lv_textarea` → `lv_label`

`lv_textarea` 是 LVGL 里最贵的对象之一（内含 label + 光标 + 游标层），
而本项目根本没有屏幕键盘（URL 靠串口 `browser <url>` 输入）。
换成 `lv_label` + `LV_LABEL_LONG_DOT` 截断，URL 真值由 `g_currentUrl` 维护。

### 6. `mem` 命令：一次纠正，和一次自己踩进去的坑

#### 6.1 纠正：别把含 PSRAM 的总堆当 DRAM

之前把"含 PSRAM 的总堆"标成 DRAM，严重误导排障。现在分开打印。

#### 6.2 ⚠️ 反过来踩的坑：不要在运行时调用 `heap_caps_get_largest_free_block()`

本文档初版曾建议"用 largest block 判断 48KB 连续栈能否分配"。**照做会导致整机重启**。

实机现象——一条 `mem` 命令打出去就崩：

```
[Console] DRAM(internal) free: 93020, PSRAM free: 7530591, total heap: 7623611
Guru Meditation Error: Core  1 panic'ed (Interrupt wdt timeout on CPU1).
Re-entered core dump! Exception happened during core dump!
Rebooting...
```

用 `xtensa-esp32s3-elf-addr2line` 解析 backtrace，PC 精确定位：

```
serial_console.cpp:130  cmdMem()
 → heap_caps_get_largest_free_block
 → heap_caps_get_info
 → multi_heap_get_info → multi_heap_get_info_impl → tlsf_walk_pool   ← PC 停在这里
```

同一时刻 Core 0 的 WiFi 收包路径：

```
ppTask → sta_rx_cb → sta_input → wifi_sta_receive → esp_netif_receive
      → wlanif_input → pbuf_alloc → memp_malloc → mem_malloc（等同一把堆锁）
```

**根因**：`heap_caps_get_largest_free_block()` / `heap_caps_get_info()` 是 **O(n) 遍历整个堆**
（`tlsf_walk_pool`），持堆锁时间以毫秒计。WiFi 在同一时刻收包要拿同一把锁 →
中断看门狗超时 → 整机重启。

| API | 复杂度 | 是否安全（WiFi 活跃时） |
|---|---|---|
| `heap_caps_get_free_size()` | O(1) 读字段 | ✅ 安全，实测多次无异常 |
| `heap_caps_get_largest_free_block()` | O(n) 遍历整堆 | ❌ **会触发 wdt 重启** |
| `heap_caps_get_info()` | O(n) 遍历整堆 | ❌ 同上 |
| `lv_mem_monitor()` | 遍历 **LVGL 自己的静态池** | ✅ 安全，不碰 ESP-IDF 堆锁 |

> 代码里已把这三条写成注释钉在 `cmdMem()` 上，别再删。

#### 6.3 现在的 `mem` 输出

```
[Console] DRAM(internal) free: 93068, PSRAM free: 7530927, total heap: 7623995
[Console] LVGL pool: used 34% (131072 B), free 88000 B, max block 65536 B
```

第二行是**关键补充**，见第 8 节。

### 7. 实机验证结果（2026-09-23 实测）

测试脚本：`tools/verify_flow.py`（一次串口连接内按时间线发命令，全程记录）。
流程：`mem` → 进浏览器加载 → `mem` → 回 launcher → `mem` → 再加载 → `mem`。

#### 7.1 连续加载：✅ 已修复

改前：第 2 次及以后必然 `Failed to create fetch task!`
改后：**连续 4 次加载全部成功**，无一次失败。

```
[Browser] fetch task created, stack=49152, DRAM free=131296   ← 启动时常驻，一次申请
[Browser] fetch_task done: result=0 layout=0x3fcda8d4 DRAM free=5104
[Browser] widgets created: 40 (limit 80)
[Browser] render done. DRAM free: 25672
```

#### 7.2 实测曲线（最终版，MAX_WIDGETS=150，桌面版 www.baidu.com）

| 阶段 | DRAM free | LVGL 池 used |
|---|---|---|
| 启动后（Launcher 常驻） | **93 028** | 19% (24 728 B) |
| 打开浏览器屏（懒创建） | 93 020（代价 48 B） | — |
| 解析完成瞬间 | **284**（峰值，剩不到 1KB！） | — |
| 渲染完成（105 widgets） | 45 028 | 40% (51 360 B) |
| **退出回 launcher** | 45 032（DRAM 不变） | **18% (23 448 B)** |
| 第 2 次加载后 | 44 996 | 40% (51 368 B) |
| 第 2 次退出后 | 44 996 | **18% (23 448 B)** |

结论：

- **退出回收完全生效**：LVGL 池 40% → 18%，回到基线，**且第二轮完全复现**。
  widget 内存是真的还了，只是还到 LVGL 池而不是 system DRAM（见第 8 节）。
- **首次加载后有 ~48KB 的常驻开销**（网络栈 / TLS / 缓存），之后**不再增长**——
  两次循环之间只差几十字节，内存是稳定的，不会再"越用越少"。
- **解析阶段只剩几百字节是最脆弱的时刻**。这是当初加 `MAX_WIDGETS` 闸门的真实原因，
  但它其实保护不了这一刻（闸门管的是渲染阶段的 widget 数，不是解析内存）。
- 两轮循环**零崩溃**（此前版本退出必崩 LoadProhibited）。

#### 7.3 退出崩溃：已修复（顺序问题）

加释放逻辑后立刻暴露新崩溃：

```
[Nav] release browser: DRAM 25764 -> 25764
Guru Meditation Error: Core  1 panic'ed (LoadProhibited).
```

根因：`nav_back_home()` 里**先销毁浏览器屏、后切屏**——销毁时浏览器还是当前活动屏幕，
LVGL 正在用这棵对象树就把它 `lv_obj_del()` 了。

修复：**先切屏，再销毁**。且不能用带动画的切换（动画期间旧屏仍参与渲染）：

```cpp
void nav_back_home() {
  if (nav_launcher) lv_scr_load(nav_launcher);   // 先切（无动画）
  nav_release_all_except(nav_launcher);          // 再销毁
}
```

> 同理，**不要在某对象的事件回调里 `lv_obj_del()` 它自己所在的屏幕**。
> 浏览器退出按钮因此只做 `BrowserScreen_close()`（清内容）+ 切屏，
> 整棵屏树的销毁交给下次进其他应用时的 `nav_release_all_except()`。

#### 7.4 Activity 懒创建后，串口命令要跟着改

改成懒创建后，串口 `nav browser` / `browser <url>` 一直报 `browser screen is null`——
因为控制台里缓存的是 `lv_obj_t*` 快照，而懒创建的屏在首次进入前永远是 `nullptr`。

修法：控制台表改存 **指针的指针**（`&nav_browser`），并在 `cmdNav` 里走 `nav_open()`：

```cpp
static ScreenEntry s_screens[] = { {"browser", &nav_browser}, ... };
...
lv_obj_t* scr = nav_open(s_screens[i].scr);   // 按需创建
```

### 8. 为什么"退出后 DRAM 没变化"——LVGL 对象池 vs system DRAM

#### 8.1 两套内存，别看错账本

`LV_MEM_CUSTOM = 0` 时，**LVGL 用自己的静态内存池**（本项目 128KB），
widget 的创建/销毁都在这个池里进出，**不经过 system DRAM**。

所以：

- 打开浏览器屏，system DRAM 只掉了 **48 字节**（纪录里 `93100 -> 93052`）
- 销毁浏览器屏，system DRAM **一点都不变**（`25764 -> 25764`）
- 但 widget 内存**确实**被归还了——归还到 LVGL 池，不是 DRAM

**要看 widget 有没有真的释放，必须看 `lv_mem_monitor()`**，这也是给 `mem` 命令加第二行的原因：

```
[Console] LVGL pool: used 34% (131072 B), free 88000 B, max block 65536 B
```

> 当初因为只盯着 DRAM，误判成"退出没释放"。实际上释放了，只是账本看错了。

#### 8.2 真正该盯的指标

| 想看什么 | 看哪个 |
|---|---|
| widget / 屏幕对象占用 | `lv_mem_monitor()` → `used_pct` |
| 任务栈、网络缓冲、HTML 解析 | `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)` |
| 大块数据（HTML、帧缓冲） | `heap_caps_get_free_size(MALLOC_CAP_SPIRAM)` |

### 9. 已知议题

#### 9.1 网页渲染"破碎"

**已修复（2026-09-23）**。

页面"破碎"的真因不是内存不够，是 `layout_engine.cpp` 里的 **`MAX_WIDGETS` 硬截断**——
画到上限就停止，后面的内容**直接丢弃**。当初加它是为了防止 DRAM 崩溃，
但它实际上保护不了最危险的解析阶段，只会在渲染阶段把页面切掉一截。

**上调的决策依据**（实测推算，LVGL 池 128KB）：

| 组成 | 占用 |
|---|---|
| 屏壳常驻 | ~23 KB（used 18%） |
| 40 个网页 widget（手机版百度） | ~15 KB → used 30% |
| 105 个网页 widget（桌面版百度） | ~28 KB → **used 40%，池仍余 79 KB** |

测前推算 150 个约需 57KB（used ~61%），实测 105 个只用 40%，有余量。

**结果**：`MAX_WIDGETS 80 → 150`，桌面版百度从 `80 (limit 80)` 变成
**`105 (limit 150)`** —— 不再触顶，页面渲染完整。

### 10. 经验总结

1. **ESP32 上"退出应用"是手动挡**：没有 MMU/GC，`lv_obj_del()` 之外没有任何东西会帮你回收。
2. **任务栈只能放内部 DRAM**，PSRAM 再多也救不了。长时间运行的后台任务应当
   **启动时创建、常驻复用**（DRAM 最充足、还没碎片时一次性申请）。
3. **别在 UI 任务里阻塞等待另一个 UI 任务的条件**——同任务串行，必然死等。改成状态机 + 排队。
4. **量内存要量对，而且要看对账本**：`xPortGetFreeHeapSize()` 含 PSRAM；
   内部 DRAM 看 `MALLOC_CAP_INTERNAL`；**widget 内存看 `lv_mem_monitor()`**。
5. **⚠️ 运行时绝对不要调 `heap_caps_get_largest_free_block()` / `heap_caps_get_info()`**——
   O(n) 遍历整堆持锁，撞上 WiFi 收包就是 wdt 整机重启（已用 addr2line 实证）。
6. **销毁屏幕时必须先切屏再删**，且不能在对象自己的事件回调里删它所在的屏幕。
7. **改成懒创建后，所有持有屏幕指针的地方都要改成"指针的指针"**，否则拿到的是过期的 `nullptr`。
8. **最贵的对象往往是被顺手用上的**：`lv_textarea` 在这个项目里根本无法输入，纯粹是浪费。
9. **改完一定要确认固件真的重编了**（见 `docs/02` 的 PIO 签名库陷阱）——
   否则你会对着旧固件的日志怀疑人生的。
