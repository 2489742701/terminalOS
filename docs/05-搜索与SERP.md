# 05 · 搜索与 SERP

> 2026-09-23 master 拍板：
> "转码代理写出来了不用它加载就没意义，只有专门做的站点才适配得了。
>  所以：**保留必应和百度作为界面**，我们自己做一个小引擎，搜索之后直接调用他们的搜索。
>  除非人家要看新闻，不然就是**广告过滤** —— 我们这里没有那么多的性能在这里。"

---

## 1. 定位：不做通用浏览器，做"能搜、能读结果"的终端

| | 通用浏览器 | 本项目（D） |
|---|---|---|
| 目标 | 尽量还原任意网页 | 只服务"搜一个问题、读几条结果" |
| 排版 | CSS 版面 | 平铺（已落地，见 docs/12） |
| 入口 | 地址栏随便输 | **搜索框 + 百度/必应两个入口** |
| 页面来源 | 任意 URL | 主要是 SERP（搜索结果页）+ 少量正文站 |
| 优化重心 | 兼容 | **过滤**（少渲染 = 省内存省时间） |

一句话：**把"渲染一切"换成"渲染值得渲染的那部分"。**

---

## 2. 架构

```
┌─ 搜索页（LVGL 自建，不是 HTML）──────────────────────┐
│  [ 搜索框 ]  [百度] [必应]                            │
└──────────────┬───────────────────────────────────────┘
               │ 关键词 → 拼 URL（UTF-8 percent-encode）
               ▼
   百度： https://m.baidu.com/s?word=<kw>       （移动版，DOM 简单）
   必应： https://cn.bing.com/search?q=<kw>
               │
               ▼
        下载（有上限，见 §4）→ Lexbor 解析 → 布局树
               │
               ▼
        **SERP 规则集**：只留"结果条目"，其余全丢
               │
               ▼
        平铺渲染：标题（胶囊，可点）+ 摘要（灰）+ 来源
```

关键点：**搜索页本身是我们自己画的 LVGL 界面**，不是加载百度的首页。
这样既省掉 700KB 首页的下载和解析，也不会出现"正在刷新/正在加载"这类占位垃圾。

---

## 3. SERP 规则集（本地，针对百度/必应的结果页结构）

目标输出：一条结果 = 3 行

```
[标题]                    ← 胶囊（蓝色框，可点，href 保留）
摘要文字……                ← 灰 #CCCCCC
来源 · 时间                ← 更小/更暗
```

规则草案（待对着真实 DOM 校准）：

| 规则 | 说明 |
|---|---|
| 只认结果容器 | 百度 `div.result` / `div.c-result`；必应 `li.b_algo` |
| 标题 | 容器内第一个有 `href` 的链接 → 胶囊 |
| 摘要 | 容器内最长的那段纯文本（> 20 字） |
| 其余全丢 | 右侧卡片、相关搜索、底部导航、页脚、脚本样式 |
| 条数上限 | 一屏 6~8 条；`MAX_WIDGETS` 兜底 200 |

> 这一步做完，"广告过滤"就完成了一大半：**不在白名单结构里的东西根本不会被渲染**。

---

## 4. 广告 / 垃圾过滤规则集

已有的（2026-09-23 落地，`layout_drop_junk()`）：

- 加载/刷新占位：`正在刷新` `正在加载` `正在编译` `加载中` `刷新中`
  `上滑加载更多` `下拉刷新` `上拉加载` `加载更多` …
- ASCII 占位：`loading` `please wait` `just a moment`（大小写不敏感）
- 纯分隔符节点：`|` `·` `>` `/` `-` `_` 单独成节点的

待补：

- [ ] 显式广告标记：文本含 `广告` `推广` `sponsored` `Ad` → 丢
- [ ] 域名/链接过滤：跳转中间页（如百度 `/link?url=` 之外带 `&tn=` 推广参数）
- [ ] 图片/脚本/样式节点一律不渲染（图片目前给占位块，见 docs/12 §6）
- [ ] Emoji / 非 BMP 字符（U+FFFF 以上）丢掉 —— 现在还是豆腐块

## 5. 性能账（为什么必须"少渲染"）

ESP32-S3 @240MHz，内部 DRAM 只有 ~345KB，可用 ~250KB：

| 环节 | 实测 |
|---|---|
| 下载 768KB HTML | 数百 ms ~ 数秒（chunked，每 4KB 让 WiFi 喘气） |
| Lexbor 解析 208 节点 | DRAM 峰值探到 166KB free |
| 平铺渲染 | 208 节点 → 245 ms |
| 屏 | 480×480，一屏只放得下 ~12 行 |

结论：**能看得见的只有十几行，下载解析几百 KB 里的绝大多数内容都是浪费**。
所以"少渲染"不只是为了好看，是这台机器的生存问题。

## 7. 实测：百度 vs 必应（2026-09-23，KitKat 移动 UA）

| | 百度 `m.baidu.com/s?word=esp32` | 必应 `cn.bing.com/search?q=esp32` |
|---|---|---|
| 页面体积 | **2.93 MB**（`<head>` 就 380KB） | **59 KB** |
| 786KB 下载上限 | 撞满截断（`cap hit mid-chunk`） | 轻松装下（59.9KB） |
| DOM 节点 | 94（截断后） | 70 |
| 渲染结果 | 27 widget，**只有筛选栏，没有一条搜索结果** | 23 widget，**5 条真实结果**（espressif / docs.espressif / csdn / espressif-modules / zhihu） |
| 可点链接 | 17 | 12 |
| 结果是否静态 | 大概率靠 JS 渲染 | **是**（`li.b_algo` ×10，`<h2>` 标题 + `<a href>`） |

**结论：默认引擎改成必应。** 百度保留为可选项，但在 786KB 上限下它根本到不了正文
（body 从 379KB 才开始，2.93MB 的页面要吃下得把上限抬到 3MB+，解析期 DRAM 扛不住）。

`m.baidu.com/` 门户页只有 193KB，能完整下载，但平铺后只剩导航和搜索框 —— 这就是为什么
首页干脆不抓网页、自己画。

## 8. 已经踩过并解决的两个坑

### 8.1 别在自己的事件回调里删自己

`startFetch()` 里有 `lv_obj_clean(g_content)`。如果在胶囊/按钮的 `LV_EVENT_CLICKED`
回调里直接调它，等于在 LVGL 事件派发循环中把该对象（连同它的 event dsc 链表）free 掉
→ 百分百 LoadProhibited。

**解法：延迟导航。** 点击回调只把 URL 写进 `g_linkPending`，真正的
`historyPush + setUrlText + startFetch` 放到下一个 `BrowserScreen_tick()` 执行。
搜索框的「搜索」按钮、常用词胶囊走的都是同一条通道。

### 8.2 导航必须用绝对 URL

`LayoutNode` 有三个 href 字段：`href`（原始属性，可能相对）、`href_resolved`
（`dom_renderer` 用 `document_url` 解析过的**绝对**地址）、`href_path`
（`extract_path()` 去掉 scheme+host 的纯路径）。

旧代码优先取 `href_path` —— 那是给显示用的，拿去重新 fetch 连主机都没有，必然失败。
现在统一走 `flat_link_target()`：**优先 `href_resolved`**，缺失才退 `href`/`href_path`，
app 层 `resolveMaybeRelative()` 再做一次兜底（补当前页 scheme+host）。

### 8.3 URL 必须 strdup

布局树渲染完就被 `tactilebrowser_free_layout()` 释放了，`href*` 指针全悬空。
`register_link_handler` 里 malloc 一份副本，靠 `LV_EVENT_DELETE` 回调回收
（`lv_obj_clean` 会逐个 child 触发 DELETE，不会漏）。

## 9. 遗留风险 / 待办

- **键盘只能敲 ASCII**：`lv_keyboard` 是英文键盘，没有拼音输入法，
  所以搜索框目前只能输英文/数字。中文查询靠「常用词」胶囊预设，
  真要中文输入得自己写拼音 IME（不小的工程）。
- 百度/必应的 SERP 结构会变，规则集需要能"降级"：抽不出结果条目时退回整页平铺，
  而不是白屏。
- HTTPS 证书校验目前是跳过的（为了省内存），仅适合自己玩。
- `render done` 里 `scrollable` 经常是负的（布局还没重算就取的值），
  不是内容没渲染 —— 看 `[Flat]` 行数和 `widgets created` 才准。

## 10. 必应 SERP 实测：UA 决定一切（2026-09-23）

### 10.1 现象

master 报："搜索里为什么是「全部 / 24小时 / 一周内 / 一个月内 / 去年」？点进去跳到很奇怪
的地方。正常只有「下一页」是必应的搜索页 —— 是不是『下一页』有特殊的『第五』没被锁到？"

不是"锁错"，是**必应对我们这个客户端做了降级**，而且降级的开关就是 UA。

### 10.2 域名矩阵（先排掉一个假线索）

`www.bing.com` 会被**地域 302** 到 `cn.bing.com`。所以匹配 UA 的域名写 `bing.com`，
两个都覆盖；别拿 `www` 的测试结果去推断设备的行为。

### 10.3 UA × 结果数 × 分页（cn.bing.com/search?q=esp32，PC 复现）

| UA | 体积 | `li.b_algo` | 分页标记 | `first=` 链接 |
|---|---|---|---|---|
| KitKat / Chrome30（移动） | 60 KB | **5** | 0 | 0 |
| Android 13 / Chrome120（移动） | 60 KB | **5** | 0 | 0 |
| iPhone / Safari17（移动） | 180 KB | **5** | 0 | 0 |
| **桌面 Chrome 120** | **100 KB** | **10** | 有 | **3** |

**结论：必应必须换桌面 UA。** 移动 UA 拿到的是阉割版 —— 5 条结果、HTML 里零个分页
标记、`first=` 参数被服务端直接忽略。桌面 UA 给 10 条 + 真的「下一页」。

体积从 60KB 涨到 ~100KB 完全可接受（平铺模式本来就跳过外部 CSS，不会变成几十次 TLS）。
百度仍走 KitKat（桌面 UA 会撞 wappass 验证码），所以 UA 是**按域名选**的。

### 10.4 「下一页」其实是假的（重要）

带桌面 UA 后，分页链接长这样：

```
<a href="/search?q=esp32&FPIG=<32位hex>&first=11&FORM=PERE">2</a>
<a href="/search?q=esp32&FPIG=<32位hex>&first=21&FORM=PERE1">3</a>
<a title="下一页" href="/search?q=esp32&FPIG=<32位hex>&first=11&FORM=PORE">下一页</a>
```

`FPIG` 是必应从上一页下发的 token。三种翻页方式全试过：

| 方式 | 与第 1 页相比的新增结果 |
|---|---|
| 裸 `&first=11`（不带 FPIG） | 0 |
| 带 FPIG + `first=11` | 0 |
| 带 FPIG + cookie 会话 + `Referer` + `first=11` | 0 |

**必应对无 JS、无历史 cookie 的客户端只下发一份固定的 ~10 条语料**，翻页链接会返回，
但内容几乎不变。所以「下一页」是官方入口、留着给用户翻，但别指望它翻出新东西。
数字页码「2」「3」纯装饰，直接丢。

### 10.5 其它引擎：都不可用

| 引擎 | 结果 |
|---|---|
| DuckDuckGo `html/` `lite/` | 本机网络**超时**（不可达） |
| Mojeek / searx.be / searx.tiekoetter / priv.au / Brave | 全部**超时**（不可达） |
| Marginalia | 可达，但搜不到东西 |
| 360 `m.so.com/s?q=` | 351 KB，14 条；`pn=` 被忽略，无「下一页」 |
| 搜狗 `m.sogou.com` | 296 KB；「下一页」是 JS「加载更多」按钮，不是链接 |
| 百度 `m.baidu.com/s` | 2.7 MB，超 786KB 上限 |

**结论：只能在中文引擎里选，且没有一个能提供真分页。** 必应 + 桌面 UA 是最优解
（100KB / 10 条 / 有官方入口）。

### 10.6 已落地的过滤（`flat_is_serp_chrome_link()`）

SERP 壳子不是搜索结果，却在平铺里全变成胶囊，点了还跳到重复页。丢这些：

| 判据 | 对应壳子 |
|---|---|
| `filters=ex1` | 24小时 / 一周内 / 一个月内 / 去年 |
| `qpvt=` | 「全部」「时间不限」「网页」标签 |
| `FORM=HDRSC` | 顶部导航：图片 / 视频 / 学术 / 词典 / 航班 |
| `/images/search` `/videos/search` `/academic/search` `/dict/search` `/travel/search` `/maps/` | 垂搜入口 |
| `first=` **且文本是 1~3 位纯数字** | 数字页码「2」「3」 |
| `FORM=PORE` | ⚠️ **反向白名单：永远保留**（这是「下一页」） |

垃圾文本短语另加：`切换到国际版` `时间不限` `搜索工具` `分页`。

### 10.7 三个连带踩到的坑

**① 容器连坐。** `<li>` 会从子树继承 `href_resolved`（`dom_renderer.cpp` 的
`subtree_first_href()` 只对 li 做，为了让搜索结果整条可点）。分页容器
`<li class="b_pag">` 因此也带着 `first=11`，**无条件按 `first=` 删会把它整块连坐掉**，
「下一页」跟着消失。修法：`first=` 只在**文本是 1~3 位纯数字**时才删。

**② `li_has_block_children()` 的门槛。** 分页 `<li>` 只有一个 `<nav>` 子元素，够不到
「≥2 个块级子元素」，于是整块文本被抽成一行 `- 分页123下一页`。修法：`nav/ul/ol/table`
这种结构容器出现一个就判定为有块级子元素。

**③ 诊断 dump 有 60 行上限。** `[Flat]` 日志写死 `s_widgetCount <= 60`，排在后面的行
（比如分页）永远打不出来，会误判成"没渲染"。已改成运行时可调：串口 `flatdump <n>`。
