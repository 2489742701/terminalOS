## 1. 字体分工（master 定的方向）

| 内容 | 谁负责 | 说明 |
|---|---|---|
| 英文 / 数字 / 半角符号 | **LVGL 内置 montserrat** | `lv_conf.h` 的 `LV_FONT_DEFAULT = &lv_font_montserrat_14`。ESP32 本来就支持，**不要编进中文字体** |
| 汉字 + 中文标点 | 自生成的 `font_zh_16` | 网页内容 + UI 正文都用它 |
| 缺字兜底 | `font_zh_16.fallback = &lv_font_montserrat_16` | 字体里没有 ASCII，靠 fallback 补，否则英文数字会整个消失 |

`lv_conf.h` 里 `LV_USE_FONT_PLACEHOLDER = 1` —— 缺字时 LVGL 画一个**方框**。
看到「方框/豆腐块」就是缺字，不要往渲染器上找原因。

## 2. 旧字体真正的毛病：不是乱码，是**字太少**

> ⚠️ 曾经误判成"生成时编码损坏、落进去的是乱码"。那是**错的**，见 §4 的解码陷阱。

正确事实（用 §4 的正确解码测得）：

| | 码位 | 汉字 | 高频22字 | 百度首页导航 |
|---|---|---|---|---|
| 旧 `font_zh_16` | 656 | **521** | 缺 0/22 | **缺 8/22** |
| 新 `font_zh_16` | 3781 | **3755** | 缺 0/22 | 缺 0/22 |

旧字体是**有意的 UI 子集**（521 个 UI 用字 + ASCII），UI 文案完全够用，
所以界面一直看着正常；但网页一旦出现表外的字就没字形 → 画方框或空白。
这就是「百度首页只显示零星几个词」的根因 —— **不是渲染器坏了，是字库不够**。

## 3. 生成流程（可复现）

```
python tools/gen_font_symbols.py tools/font_symbols.txt     # 1) 生成字符集（UTF-8 文件）
node   tools/gen_font.js 16 4 tools/font_symbols.txt src/app/font_zh_16.c
```

- 字符集：**GB2312 一级字库 3755 字**（日常中文覆盖 99%+）+ 中文标点 `，。、！？；：（）《》【】…—·～￥％＃＠　`。
  不含任何 ASCII。要二级字库（+3008 字）加 `--level2`，但 flash 会再翻一倍，一般不必。
- 源字体：`C:\Windows\Fonts\simhei.ttf`，16px，bpp 4。
- `gen_font.js` 用 `spawnSync` 传 **argv 数组**，不走 shell —— 这点很关键，见 §5。
- `gen_font.js` 会**自动后处理**挂 fallback（见 §6），不要跳过。

产物：`font_zh_16.c` 约 **2.7 MB**（旧版 413 KB），编译进固件约 **+470 KB**。
当前固件约 2.3 MB，app 分区 ~3.9 MB，够用。

`font_zh_24`（标题用，24px）**没有重新生成** —— 它只服务 UI 标题，
原来那 521 字够用，重做成 3755 字要 +1 MB 以上，不划算。

## 4. ⚠️ 解码陷阱：sparse cmap 存的是**相对偏移**，不是绝对码位

要检查一个字体到底有哪些字，**必须**按 LVGL 的方式解码：

```c
// lv_font_fmt_txt.c: get_glyph_dsc_id()
uint32_t rcp = letter - cmaps[i].range_start;      // 相对码点
// LV_FONT_FMT_TXT_CMAP_SPARSE_TINY:
uint16_t key = rcp;                                 // ← 二分查找用的是 rcp
```

所以：

- `FORMAT0_TINY`（连续段）→ 绝对码位 = `range_start .. range_start + range_length - 1`
- `SPARSE_TINY`（稀疏）→ **绝对码位 = `range_start + unicode_list[n]`**

**直接把 `unicode_list` 里的值当 Unicode 码位会得出完全错误的结论** ——
本人就因此把一份正常的 521 字字体误判成"韩文/希腊字母/生僻字乱码"。
（`0x1de3` 不是"这个码位"，而是 `12317 + 0x1de3 = 0x4E00` = 一。）

判断字体好坏请用 `tools/` 下带正确解码的脚本，别手搓正则后直接读 `unicode_list`。

## 5. 为什么必须绕开 shell

上一版字体是用命令行 `--symbols "啊阿埃…"` 传的。Windows 的 cmd / PowerShell 里
`! $ & * ( ) [ ] { } ; ' " < > | ^ \ ` 全是元字符，中文还会被代码页二次编码 ——
几千字的参数极容易被破坏。

对策：**字符集先写进 UTF-8 文件，再由 Node 读出、以 argv 数组传给 lv_font_conv**
（`spawnSync` 不经 shell）。字节级无损，且可复现。

## 6. fallback 必须挂，而且要挂在生成产物里

LVGL 8.3 **没有** `lv_font_set_fallback()`，而 `font_zh_16` 被声明成 `const lv_font_t`，
运行时改不了 `.fallback` 字段。所以 `gen_font.js` 在生成后直接改文件：

```
.fallback = NULL,   →   .fallback = &lv_font_montserrat_16,
并在 include 之后插入 extern const lv_font_t lv_font_montserrat_16;
```

**每次重新生成都会重新执行这一步**（已写进脚本）。手工改过又被覆盖的话，
先想想是不是该改脚本而不是改产物。

`lv_font_montserrat_16` 必须在 `lv_conf.h` 里开着（现在 `LV_FONT_MONTSERRAT_16 = 1`）。
