# 显示花屏（刷新瞬间乱码）排查与修复

> 适用硬件：ESP32-S3（16MB Flash / 8MB OPI PSRAM） + 4.0" 480×480 ST7701S RGB 并行屏 + GT911
> 结论状态：**已解决**（2026-09-22 实机验证，静态与刷新均无花屏）

---

## 1. 现象（决定性线索）

> **静态画面完全正常，只有在画面刷新的那一瞬间出现乱码 / 撕裂 / 花屏。**

这一条是整个排查的转折点。它把问题域从「屏幕初始化/时序配错了」直接收敛到「**总线带宽争抢**」：

| 若根因是… | 症状应该是… |
|---|---|
| ST7701S 初始化序列 / 3-wire SPI 配错 | **全程花**或白屏、偏色，静态也不会干净 |
| RGB 时序（porch / PCLK 相位）配错 | 画面整体偏移、撕裂线固定在某行，静态同样异常 |
| **PSRAM 带宽被抢、LCD DMA 饿死** | **静态干净（DMA 独占带宽），只在 CPU 并发写 PSRAM 的刷新瞬间乱码** ✅ |

---

## 2. 根因

```
                        ┌──────────── OPI PSRAM 总线（唯一一条）────────────┐
                        │                                                  │
   CPU 侧  ── LVGL 渲染写帧缓冲 ──┐                                        │
           ── I2C 读 GT911 ───────┼──► 争抢带宽 ──► LCD DMA 取不到数据 ──┐  │
           ── Cache_WriteBack ────┘                                      │  │
                                                                         ▼  ▼
   LCD 侧  ── RGB 外设 DMA 恒定读帧缓冲（带宽 = PCLK × 2 字节，一刻不停）──► 输出旧数据/垃圾数据
```

- 帧缓冲分配在 **PSRAM**（`MALLOC_CAP_SPIRAM`），不是内部 SRAM。
- LCD RGB 外设靠 DMA **恒定**从 PSRAM 抽像素流，占用带宽 = `PCLK × 2B`（RGB565）。
  - PCLK = 16MHz → **32 MB/s** 常驻占用。
- OPI PSRAM @80MHz 的理论峰值带宽在几十 MB/s 量级，扣除 ECC/刷新/仲裁开销后，CPU 与 DMA 并发时余量很小。
- 只要 CPU 在同一时刻读写 PSRAM（LVGL 渲染、cache 回写、I2C 触摸轮询），DMA 就会**饿死**若干拍，这几拍 LCD 输出的不是新像素，而是旧数据 / 未定义数据 → 刷新瞬间花屏。
- **画面静止时**没有 CPU 写 PSRAM，DMA 独占带宽，所以画面完全干净 —— 与观测现象完全吻合。

**Espressif 官方对这类问题的标准解法就是：降 PCLK，给 PSRAM 留带宽余量。**

## 3. 有效修复（按贡献度排序）

### ✅ 3.1 降 PCLK：16MHz → 10MHz 【决定性修复】

`src/config/pins.h`：

```cpp
constexpr uint32_t RGB_BUS_SPEED = 10000000;  // 10MHz（降 PCLK 给 PSRAM 留带宽，抗 DMA 饿死花屏）
```

带宽账：

| PCLK | DMA 常驻带宽 | 留给 CPU | 理论刷新率* |
|---|---|---|---|
| 16 MHz | 32 MB/s | 紧张 | ≈ 56 fps |
| **10 MHz** | **20 MB/s** | **+12 MB/s 余量** | **≈ 35 fps** |

\* 刷新率 = `PCLK / ((480+10+8+50) × (480+10+8+20))` = `PCLK / 283,864`。
35 fps 对静态 UI（Launcher / 时钟 / 设置）完全够用，实测无拖影感。**这是本项目的默认配置，不要改回 16MHz。**

### ✅ 3.2 LVGL 绘制缓冲：恢复 PSRAM 双缓冲，每缓冲 120 行（≈1/4 屏）

`src/app/app.cpp`：

```cpp
// PSRAM 双缓冲，每缓冲 120 行 ≈ 1/4 屏
uint32_t bufSize = SCREEN_WIDTH * 120;          // 57,600 px / 115,200 B
dispBuf1 = (lv_color_t*)heap_caps_malloc(sizeof(lv_color_t) * bufSize, MALLOC_CAP_SPIRAM);
dispBuf2 = (lv_color_t*)heap_caps_malloc(sizeof(lv_color_t) * bufSize, MALLOC_CAP_SPIRAM);
lv_disp_draw_buf_init(&drawBuf, dispBuf1, dispBuf2, bufSize);
```

- **双缓冲**：一个在 flush 的同时，LVGL 可以渲染下一个，避免渲染与 DMA 严格串行。
- **缓冲行数不能太小**：太小会让 LVGL 把一屏拆成大量小批次 flush，每次 flush 都伴随 DMA 启停 + `Cache_WriteBack`，**反而加剧带宽争抢**。120 行是实测稳定的取值。
- 串口验证：`[App] buf pixels=57600 bytes=115200 ptr=0x3d8712dc` —— 地址 `0x3d...` 即 PSRAM 段，确认生效。

> ⚠️ **诚实标注**：本次没有做「只改缓冲、不动 PCLK」的单一变量对照实验，因此**无法精确拆分**「PCLK 降频」与「缓冲回退」各自的贡献。判定依据是现象与带宽模型（静态干净 = 带宽争抢），降 PCLK 是官方标准解法，故列为主因。

### ✅ 3.3 触摸 10ms 去抖（减少总线打扰）

`src/app/app.cpp::touchRead()`：

```cpp
static uint32_t lastMs = 0;
uint32_t now = millis();
if (now - lastMs >= 10) {       // 10ms 窗口内复用上次结果
  lastMs = now;
  int x, y;
  lastDown = Touch::hasSignal() && Touch::touched(x, y);
  ...
}
```

原本每次 `lv_timer_handler()` 都发起一次 I2C 读 GT911；I2C 事务会周期性打断 PSRAM 访问。加时间窗后总线上少了一类周期性打扰源。

### ✅ 3.4 `loop()` 中的 `delay(5)`（本来就有，保留）

`src/main.cpp` 末尾 `delay(5)` —— 避免 CPU 100% 空转抢总线，给 DMA 与空闲任务喘息。**不要删。**

## 4. 花屏的直接诱因：另一个 AI 改坏了缓冲配置

现象是「别人烧录后就花屏了」。定位手法：

```bash
git diff                       # 找出唯一功能性改动
```

**唯一功能性改动**：`app.cpp` 的 LVGL 绘制缓冲被从 `100 行 · PSRAM · 双缓冲` 改成
`200 行 · 内部 RAM · 单缓冲`。

关键点：**这个改动不会让程序崩溃**。串口证明其启动完全正常（缓冲分配成功、`init ok`、`ready`），
所以「看串口有没有报错」这种检查是抓不到它的 —— 必须靠 `git diff` 看改了什么。

改动后的坏处：
- **单缓冲**：flush 期间 LVGL 无法继续渲染 → 渲染与 DMA 严格串行化。
- **内部 RAM**：容量紧张（200×480×2 = 192KB），且与 `Cache_WriteBack` 的交互更频繁。

修复：回退为 PSRAM 双缓冲，并顺带把行数调整为 120 行。

| 嫌疑 | 结论 | 证据 |

## 6. 社区流传方案在本技术栈的可行性（已核实，别浪费时间）

当前栈：**Arduino core 2.x / IDF 4.4**（`platform = espressif32@^6.0.0` + `framework = arduino`）。

| 社区方案 | 状态 | 原因 |
|---|---|---|
| 启用 Bounce Buffer（`bounce_buffer_size_px`） | ❌ 不可行 | `esp_lcd_rgb_panel_config_t` 在 IDF 4.4 **没有**该字段，是 IDF 5.x 才引入的 |
| `CONFIG_ESP32S3_DATA_CACHE_LINE_64B=y` | ❌ 不可行 | sdkconfig 中 `is not set`，且 Arduino 框架下**没有 menuconfig** 可改 |
| 禁用 `CONFIG_LCD_RGB_RESTART_IN_VSYNC` | ❌ 不可行 | 该配置项在当前 IDF 版本**不存在** |
| VSYNC 事件回调 / 双帧缓冲交换消除撕裂 | ❌ 不可行 | `esp_lcd_rgb_panel_register_event_callbacks` 是 **IDF 5.x** API；IDF 4.4 只有老式 `on_frame_trans_done`，拿不到 VSYNC |
| 把缓冲挪到内部 SRAM 规避 PSRAM | ⚠️ 无效（已试） | 就是本次花屏的直接诱因（见第 4 节） |

**结论：在本栈下，降 PCLK 是唯一能真正落地的主干手段。** 若将来必须上 Bounce Buffer / VSYNC 同步，需要整体升级到 ESP-IDF 5.x（放弃 Arduino 框架或迁到 `arduino-esp32` 3.x）。

## 7. 排查手法沉淀（可复用）

1. **先问「静态正不正常」** —— 一句话区分「配置错」与「带宽争抢」。
2. **别人改崩了 → `git diff` 先于一切猜测**。别凭现象猜代码。
3. **串口正常 ≠ 配置没问题**。缓冲位置/大小这类改动崩溃都懒得崩，只表现为显示异常。
4. **交叉验证烧的是哪一版**：产物时间戳（`.wb_build/esp32s3/*.bin`） vs 源码时间戳 vs 串口打印的 `ptr=`，三者对齐才算数。
5. **改显示相关配置前先算带宽账**（`PCLK × 2B`），不要凭感觉调。
