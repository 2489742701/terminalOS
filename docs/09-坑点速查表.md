## A. 开不了机 / 无限重启

### A1 · `rst:0x3` 无限重启，**没有任何 panic 输出**
- **根因**：不是崩溃，是**主动死循环**。多半是分区表越界 → bootloader 进 `while(1)` → 被 RTC 看门狗复位。
- **动作**：⛔ 立即检查有没有配 `board_build.flash_size = 16MB` 或 `partitions_16MB.csv`。板子物理是 16MB，但**本工程编译出的 bootloader 只认 8MB**。删掉，用默认 8MB 分区。
- **另查**：`Saved PC` 是否恒定。恒定 = 死循环；每次不同 = 真崩溃。
- **详见**：[`01` §1.4](01-板级硬事实与构建烧录.md) / [`07`](07-排障方法论.md)

### A2 · 卡在 bootloader，每秒一次 TG0WDT 复位
- **根因**：Flash 模式配成 QIO。这块板必须 **DIO**。
- **动作**：`board_build.flash_mode = dio`；**裸 esptool 直烧也必须带 `--flash_mode dio`**。
- **详见**：[`01` §1](01-板级硬事实与构建烧录.md)

### A3 · PSRAM 相关异常 / 缓冲没落在 PSRAM
- **根因**：PSRAM 线模式。这块板是 **OPI**。
- **动作**：`board_build.arduino.memory_type = qio_opi`。
- ⚠️ **DIO 与 OPI 必须同时成立**，缺一开不了机。
- **成功标志**：`ptr=0x3d8712dc`（`0x3d…` = PSRAM 段）。
- **详见**：[`01` §1](01-板级硬事实与构建烧录.md)

### A4 · 不知道是崩溃还是死循环
- **动作**：用极简工程二分 —— `tools/minimal_run.py`。连极简工程也挂 ⇒ 是配置问题，不是你的代码。
- **详见**：[`07`](07-排障方法论.md)

## B. 显示异常

### B1 · 刷新瞬间花屏 / 撕裂 / 噪点
- **根因**：**带宽争抢** —— 帧缓冲在 PSRAM，RGB 并行 + GDMA 靠 bounce buffer（须内部 DMA 内存）中转，PSRAM OPI 80MHz 与片内 flash 同一条总线分时复用。
- **已定的解**：`PCLK = 10MHz`（**别改回 16**）；LVGL 缓冲 PSRAM 双缓冲 × 120 行。
- **分水岭判据**：静态正常、只刷新时乱 → 带宽争抢；**静态也花** → 时序错（去查 ST7701S 时序）。
- **详见**：[`02`](02-显示-花屏与ST7701S.md)

### B2 · ST7701S 配置别动
`st7701_type1_init_operations` + RGB 时序 H 10/8/50、V 10/8/20、IPS/BGR=true。这几个值都是试出来的，**不要"顺手优化"**。

### B3 · 上滑时左下角一条白线
**2026-09-24 定位 + 修 + 上板确认已消失**：LVGL 的滚动条。
`lv_obj` 默认 `LV_SCROLLBAR_MODE_AUTO`（`lv_obj.c:348`），可滚动时沿边沿画一条
滚动条；本工程没给 `LV_PART_SCROLLBAR` 设自定义样式，用的是默认浅色 ——
在黑底 UI 上就是一条白线，且只在"内容比容器长"时出现，跟"上滑"高度相关。

- `desktop_screen.cpp` 早就 `lv_obj_set_scrollbar_mode(cont, LV_SCROLLBAR_MODE_OFF)`，
  `browser_screen.cpp` 的 `g_content` **漏了** → 已补。
- **自查方法**：任何可滚动容器都要显式设 `LV_SCROLLBAR_MODE_OFF`（或给 SCROLLBAR
  设一套暗色样式）。`grep -rn "scroll_dir" src/` 找出所有可滚动对象逐个核对。

### B3b · 触摸坐标偏移（2026-09-24 定位）
根因有两个，都在 `src/hal/touch.cpp` 的映射表达式里：

1. **翻转了两次**：TAMC_GT911 库 `setRotation(ROTATION_NORMAL)` 已经做过
   `x = width - x`，旧代码又 `map(p.x, 480, 0, 0, 479)` 翻一次 —— 两者对消，
   实际等价于"裸值 ×479/480"。看代码像是翻转，其实没有。
2. **端点写死 480**：若 GT911 配置寄存器里的 `X/Y_OUTPUT_MAX` 不是 480，
   裸值根本不落在 0..480，于是整屏偏移/缩放都不对。

**已改**：两点线性映射 + 三个串口命令 ——
`tprobe`（读 GT911 的 X/Y_OUTPUT_MAX，不是 480 就是根因 2）、
`traw [s]`（10s 内连续打裸坐标，逐个点四角）、
`tcal x0 x1 y0 y1`（填实测端点，立即生效，不用重烧）、
`tswap [on|off]`（X/Y 交换，面板贴反时试它）。
默认值 0/480/0/480 只为了复刻旧行为，**不是真值**。

2026-09-24 实测 `tprobe`：**X/Y_OUTPUT_MAX 都是 480，与屏幕一致** ——
根因 2 排除。那么只剩三种可能：轴向翻转（用 `tcal 480 0 480 0` 试）、
X-Y 交换（用 `tswap` 试）、常量偏移（用 `traw` 量四角后填端点）。

### B4 · IDF 4.4 升不了级
别浪费时间试，此路不通。

### C5 · 退出/切屏时崩

### C8 · ⚠️ `A stack overflow in task loopTask has been detected`（2026-09-23 实测）

**症状**（极易误判成"内存不够"）：
- 打开某个网页时整机重启
- **画面还停着，但触摸完全失效** —— RGB 并行屏由 GDMA 自行刷新，
  主任务已经死了，DMA 还在刷最后一帧
- 串口在重启前会明确写：
  `***ERROR*** A stack overflow in task loopTask has been detected.`
- `Backtrace` 结尾常带 `|<-CORRUPTED`（栈被打烂，回溯不可信）
- **跟内存无关** —— 实测出事时 DRAM 还剩 203KB

**根因：是栈不是堆。**
Arduino-ESP32 的 `loopTask` 栈默认只有 **8192 B**。而 layout_engine 里有 4 个
全树遍历函数把 `next_sibling` 也写成了递归：

```c
layout_tree_stats        / layout_flatten_tree
layout_scale_tree        / layout_clamp_horizontal
    ...
    f(node->first_child, ...);
    f(node->next_sibling, ...);   /* ← 凶手 */
```

于是递归深度 = **树的节点总数**（几百到上千），而不是嵌套层数。
必应搜索页 356 个节点侥幸过关，乐鑫官网 977 个节点直接炸。

**怎么判别**：报错里写的是 `task loopTask` = UI 主任务；
若后台任务崩，写的是 `task browser_fetch`（那是另一回事，见 D4）。

**修复（已在 2026-09-23 做完）**：
- 上面 4 个函数 sibling 改迭代：`while (node) { ...; node = node->next_sibling; }`
- `platformio.ini` 加 `-DARDUINO_LOOP_STACK_SIZE=32768`（8KB → 32KB）
- 剩下纯父子递归的 `layout_render_node` / `layout_drop_junk` 加 `MAX_LAYOUT_DEPTH 64` 上限
- ⛔ **`layout_node_destroy` 绝不能加深** —— 中途截断 = 内存泄漏
- 加了永续预警：每次渲染完串口打
  `[Browser] loopTask stack: xxxx B left (peak used xxxx B)`
  低于 ~8KB 就该回头查递归是不是又失控了

**修复后的实测对照**：同一条三级跳转路径，977 节点的页面从「必崩」变成
正常渲染，栈峰值 11108 B、剩余 21660 B。

## D. 内存

### D1 · 为什么 PSRAM 空着 7MB、DRAM 却见底
- **根因**：`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=4096` —— **≤4KB 的 malloc 一律进内部 DRAM**。
  布局树节点、`text_content`、href/class/style 拷贝全是小分配 ⇒ DRAM 被一点点榨干。
- **已定的解**：解析阶段改用 `tb_alloc` / `tb_calloc`（PSRAM 优先，malloc 兜底），
  `src/browser_engine/src/tactilebrowser_core.cpp`。实测 DRAM 开销 40KB → 4KB。
- **详见**：[`03`](03-浏览器架构与生命周期.md)

### D2 · 量化内存用错 API
- ✅ `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)` —— 这才是 DRAM
- 🚫 `xPortGetFreeHeapSize()` —— **含 PSRAM**，别当 DRAM 用

### D3 · 🚫 运行时禁调这两个
```c
heap_caps_get_largest_free_block();  // O(n) 遍历整堆持锁
heap_caps_get_info();                // 同上
```
撞上 WiFi 收包直接 **wdt 重启**。addr2line 实证过。
- **详见**：[`03` §6.2](03-浏览器架构与生命周期.md)

### D4 · 任务栈只从内部 DRAM 分配
→ 后台任务要**一次性常驻复用**（notify 唤醒），**别反复 create/delete**。
fetch 任务栈 16384（实测峰值 3712 B）。

### D5 · 无 MMU 的现实
不 `lv_obj_del()` 就永不释放。LVGL 池**已在 PSRAM**（`LV_MEM_POOL_IN_PSRAM 1`，
在 `src/config/lv_conf.h`）。开机内部 DRAM free 250KB，PSRAM 7.2MB。
别想"运行时搬来搬去"——两段物理地址，搬运 = 手写 GC。

### D6 · chunked 读取写穿堆
HTTPS 下载上限 786432 B。chunked 读取**必须钳 `room`/`want`**，
否则写穿 PSRAM 堆，表现为 WiFi 驱动报 `block_trim_free heap_tlsf.c:371`（看着像 WiFi 的锅）。

## F. 浏览器排版 / 渲染

### F1 · 布局压盖 / 元素零高 / 位置全乱
- **根因**：CSS 算出的 x/y/height 大量为 0，而 `create_label` 里是 `(void)x;(void)y`
  根本不消费坐标；唯一吃坐标的 `create_container` 就成了压盖/零高的源头。
- **已定的解**：**平铺模式** `layout_set_flat_mode(true)`（默认开，串口 `flat on|off`）——
  不建容器、满宽居左，症状全消。
- **路线**：A（还原 CSS 版面）已放弃，C（转码代理）不做，现走 **D 平铺 + 搜索优先**。
- **详见**：[`04`](04-浏览器排版与渲染.md)

### F2 · 行合并规则
- 无文字壳子透明钻入
- **跨壳（父不同）只放行链接**，普通文本不放行
- `<li><a>` 靠 `li_is_link_wrapper()` 保留内层 `<a>`

### F3 · 结构性容器被压成一行（如必应分页变成 `- 分页123下一页`）
- **根因**：`li_has_block_children()` 要求「≥2 个块级子元素」才拆开，
  但 `<li class="b_pag">` 只有**一个** `<nav>` 子元素，够不到门槛。
- **已定的解**：`nav / ul / ol / table` 这类**结构性容器出现一个就判块级**。
- **详见**：[`05` §10](05-搜索与SERP.md)

### F4 · 垃圾过滤 `layout_drop_junk()`
丢：正在刷新/加载/编译、加载更多、纯分隔符、`loading` 等。
必应 SERP 另丢：时间筛选 `filters=ex1`、全部/时间不限 `qpvt=`、顶部导航 `FORM=HDRSC`、
垂搜路径、纯数字页码。`FORM=PORE`（下一页）**反向保留**。
⚠️ 过滤规则要**只作用在真正的 `<a>` 上**——容器 `<li>` 会继承子树 href，
按 href 过滤会连坐删掉整棵子树（这个坑让「下一页」消失过一次）。

### F5 · 页面元素莫名整棵消失
- **根因**（百度首页搜不到搜索框的真凶）：外层 `<span>` 的图标字体字符让整棵子树被丢弃。
- **取证三步法**见 [`04`](04-浏览器排版与渲染.md)。

### F6 · ⚠️ 诊断 dump 被 60 行截断，让你误判"没渲染"
`[Flat]` 日志默认只打 60 行，**渲染本身没截断**。
排查第 60 行之后的内容（比如「下一页」）先 `flatdump 200` 再刷新。

### F7 · 链接点不动 / 点了跳错
三个坑，都已修：
1. 🚫 **别在 CLICKED 回调里 `startFetch()`**（会 clean 掉正在回调的对象）→ 走 `g_linkPending` 延迟通道，下一 tick 才导航

### F10 · ⚠️ 伪链接被当成真网页下载（`javascript:` 等）

**症状**：点网页上的空按钮 / 菜单项后，进度条走到 60~70% 停下或直接重启；
日志里出现 `read 500000+ bytes`、节点数暴涨到几千、DRAM 一次掉上百 KB。

**根因**：现代网站大量 href 根本不是真地址 ——
`javascript: void(0);`（纯 JS 空按钮，乐鑫官网菜单里一大堆）、
`mailto:` `tel:` `#anchor`。这些一旦走下载流程，服务器往往返回一个大号 404 页。

更难的是它们**常被拼上域名前缀**，变成：
```
https://www.espressif.com.cn/zh-hans/products/socs//javascript: void(0);
```
只看开头是不是 `javascript:` 拦不住，必须查**子串**。

**实测代价**（2026-09-23）：一次这种点击下载了 507440 B、解析出 4780 个节点、
DRAM 从 207KB 掉到 72KB。连点几下就该重启了。

**动作**：`isPseudoUrl()` 在两个入口拦 —— `link_click_cb` 和 `startFetch`。
判定 = 前缀命中伪协议列表（javascript:/mailto:/tel:/data:/about:/blob:/sms:/intent:/…）
**或** 子串含 `javascript:` / `void(0)` **或** 以 `#` 开头。

## H. 网络

### H1 · UA 决定一切（必应血案）
`www.bing.com` 会**地域 302 到 `cn.bing.com`**，然后按 UA 降级：

| UA | 体积 | 结果条数 | 分页 |
|---|---|---|---|
| 移动（KitKat / Android13 / iPhone） | 60KB | **5** | **无** |
| **桌面 Chrome120** | 100KB | **10** | 有「下一页」 |

- **已定的解**：**必应走桌面 Chrome120 UA**；百度/其它仍走 KitKat（避免 wappass 验证码）。
  在 `lvgl_renderer.cpp` 里按 host 分支。
- ⚠️ 桌面 UA 给百度会被 302 到 `wappass.baidu.com` 验证码页。

### H2 · 「下一页」是假分页
链接带 `FPIG=<32位hex>` token，但裸 `first=11`／带 FPIG／再加 cookie+Referer，
**三种方式与第 1 页相比新增结果都是 0**。必应对无 JS 客户端只下发固定约 10 条语料。
（`first=` 被服务端直接忽略。）

### H3 · 换引擎这条路是死的（都实测过）
| 引擎 | 结果 |
|---|---|
| DDG / Mojeek / searx / Brave | 此网络**全部超时** |
| 360 | 351KB，`pn=` 无效 |
| 搜狗 | 「下一页」是 JS 按钮 |
| 百度 `m.baidu.com/s?word=` | **2.93MB**（head 就 380KB），786KB 上限连正文都摸不到 |

### H4 · HTTPS 上限 786432 B
见 D6。

### H5 · NTP
`src/hal/ntp_time.cpp` 手写（🚫 勿用 NtpClientLib，会塞回 `Time` 库）。
⚠️ `ntp.aliyun.com` 间歇超时，**必须多服务器兜底**。

### H6 · HTTP 要跟 3xx
不跟的话 `www.baidu.com` 302→https 会被判成"网络错误"。已加 Location 递归（5 跳）。

### H7 · 内置页面服务器（下载后怎么看）
`dl` 存进 LittleFS → `serve` → PC 浏览器访问 `http://<板子IP>/` 拿原始 HTML。
⚠️ **修过的 bug**：`ls` 曾无条件 `LittleFS.end()`，会把正在跑的服务器搞成 404。
现在服务器在跑时不再卸载。

### I5 · ⚠️ 二级菜单切页：三条铁律（2026-09-24 设置页重构）
- **症状 A**：点列表行进子菜单，随机崩 / 崩在 `lv_obj_clean` 之后。
  **根因**：在行的 `LV_EVENT_CLICKED` 里 `lv_obj_clean()` 会删掉**正在分发事件的那一行**。
  **动作**：切页一律延迟一拍 —— 一次性 `lv_timer`（period=1, repeat=1）里再 clean + 重建。
- **症状 B**：列表右侧一条浅色竖条。**根因**：默认 `LV_SCROLLBAR_MODE_AUTO`。
  **动作**：可滚动容器显式 `LV_SCROLLBAR_MODE_OFF`（就是浏览器那条"白线"）。
- **症状 C**：`back` 点了什么也没发生，**而且不打日志**。
  **根因**：把**串口命令行缓冲区的指针**存进了页面栈 —— 命令一结束缓冲被下一条命令覆盖，
  `findPage()` 拿到的是 `"setpage back"` 而不是 `"general"`，找不到页就静默 return。
  **动作**：栈里只存页表里的静态字面量（`settings_menu.cpp::canonPageId`）。
- **另**：栈约定 `s_stack[s_depth] == 当前页`（栈底是 root），back = `--depth` 再取。
  写成"先写后 ++"却"先 -- 后取"会取到自己（差一错误）。
- **详见**：`src/app/settings_menu.cpp` 头注释

### I6 · `lv_timer_get_user_data()` 在本工程 LVGL 里不存在
- **症状**：编译报 `was not declared in this scope`，编译器建议 `lv_anim_get_user_data`。
- **根因**：随板 BSP 的 LVGL 是 8.3.0-dev，只给了 `lv_timer_create(cb, period, user_data)`，
  没有配套的 getter。
- **动作**：在读侧直接取结构体字段 `t->user_data`（`lv_timer_t` 的成员是公开的）。
- **详见**：`src/app/status_bar.cpp::back_async_cb`

## J. 工具 / 环境（Windows 特供）

### J1 · ⚠️ Edit 工具会报成功但不落盘
本项目 **CRLF 文件上已踩 6+ 次**。
**每次编辑后必须 grep 回读核对**；不确定就用托管 python 做字符串替换 + 立即校验。

### J2 · bash shim 是坏的
`ls` / `head` / `grep` / `tail` / `dirname` 都 not found，`rc=127` **不代表命令失败**。
→ 用 PowerShell 或托管 python 代替。
⚠️ `build_run.py 2>&1 | tail -40` 会因为 `tail` 不存在而"失败"。

### J3 · 写文件别用反引号
会被命令替换吃掉。

### J4 · PowerShell 常不回显 stdout
→ 用 `*>` 重定向到文件（UTF-16），再用托管 python 解码读取。

### J5 · 生成/传参绕开 shell
字符集或参数里有中文/特殊字符 → 写文件 + Node `spawnSync` 传 argv 数组。
