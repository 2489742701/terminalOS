## 一、排版路线：为什么走平铺（路线 D）

### 2. 为什么 A（还原 CSS）走不通 —— 有实锤，不是借口

#### 2.1 根因：唯一吃绝对坐标的是容器，而 CSS 算出来的坐标是垃圾

代码层面的三件事（这是关键，之前一直没看穿）：

1. `lvgl_renderer_create_label()` 里是 `(void)x; (void)y;` —— **label 根本不用布局引擎算的
   x/y**，位置交给父容器的 flex 排。所以几何算错对 label 没影响。
2. 唯一吃绝对坐标的是 `create_container()`（`lv_obj_set_pos(container, x, y)`）。
   CSS 算出的 x/y/height 在本引擎里大量是 **0 或离谱值** → 容器互相压盖、零高度、
   子元素整体不可见。
3. `layout_should_be_row()` 还会把容器切成 `LV_FLEX_FLOW_ROW` → 内容一路往右溢出，
   配合 label 的 `lv_pct(100)` 必然戳出右边界。

→ **不建容器，1/2/3 同时消失。** 这就是平铺能根治"排版混乱"的原因。

#### 2.2 量化的绝望

`http://www.baidu.com/` 实测：`nodes=400`，但 `contentH = 187px`（可视区 414px）。
PC 站大量使用 **float / position:absolute / flex / grid**，本引擎一个都不支持，
绝大多数块被算成 0 高，页面直接塌掉。
**横向钳制救不了"高度为 0"** —— 这是为什么之前加了 clamp 也没用。

#### 2.3 真要做通用 CSS 排版要付什么

- 层叠与优先级（specificity）、继承、默认样式表
- float / clear、BFC、position、flex、grid
- 行内格式化上下文（line box、baseline 对齐）
- 字体度量与 text shaping（本项目的 `estimate_text_width()` 是
  `strlen * fontSize * 0.6`，对 UTF-8 中文直接高估 80%）

参照 NetSurf：通用 CSS 引擎是**十万行级**的工程量。在 240MHz 的 ESP32-S3 上，
即便写出来，单次排版也可能要几百毫秒到秒级。内存不是瓶颈（8MB PSRAM 够），
**CPU 和工程量才是**。

### 3. 平铺模式（方案 B）的规则集

开关：`layout_set_flat_mode(true)`，串口 `flat on|off`（默认 on）。

#### 3.1 核心规则

1. **不创建任何容器**。只有根容器复用 `root_container`，其余 div/container 一律
   `widget = NULL`，子节点直接挂到最近的真实容器（flex column）。
2. **全部满宽、居左**。`create_label` 走 `lv_pct(100)` + `LV_LABEL_LONG_WRAP`，
   左右方向**天然不可能越界**。
3. **不再整页缩放**。之前 `scale = 464/1024 = 0.45` 会把 16px 字压到 6px；
   平铺下文字恒为最小可读字号。

#### 3.2 行内合并规则（解决"一行被拆成四行"）

导航条「我的关注 / 我的收藏 / 皮肤中心 / 用户反馈」如果各占一行，一屏就废了。
渲染前跑一遍 `layout_merge_inline_rows()` 预处理：

| 规则 | 说明 |
|---|---|
| 参与者 | 只有行内元素（a / span / strong / em / b / i / u / li）；块级元素各占一行 |
| 同种类才并 | 链接只跟链接并、普通文本只跟普通文本并 —— 否则整行会因一个链接全染蓝 |
| 折行 | 累计估算宽 > 容器宽 → 另起一行（全角 = 字号，半角 = 0.5 字号） |
| 分隔符 | 链接行 `" · "`（导航条观感），普通文本行 `" "` |
| 实现 | 把后续兄弟的文本**并进第一个兄弟**，后者 `text_content` 置空 → 渲染时不产 label |
| 壳子透明 | 自己不写字、只包子节点的节点（`<li>`、包 span 的页脚 `<div>`）不打断行，合并会钻进去继续 |
| **跨壳只并链接** | 以**直接父节点是否相同**判跨壳。同父 → 正常并；不同父 → **只有链接能继续并** |
| 一行上限 | `FLAT_ROW_MAX_ITEMS = 8`，防止整页链接被 `" · "` 串成一坨 |

##### 为什么"跨壳只并链接"这条是必须的（踩了三轮才定下来）

导航条是 `<ul><li><a>我的关注</a></li>…</ul>`，每个 `<a>` 的爹是各自的 `<li>`，
**只看同一层兄弟永远并不到一起** —— 这是"四个导航项被拆成四行"的真正原因。

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 只看同层兄弟 | — | 导航条 4 行（坏） |
| v2 壳子全透明 | 无文字壳子钻进去，不限种类 | 导航条 1 行 ✅ 但「设置 ©2026 Baidu…」「百度一下 正在刷新」串味，14 行并到 7 行（坏） |
| v3 只剥"独子壳" | `<li>` 里还有图标 span，不是独子 | 又退回 4 行（坏） |
| **v4 跨壳只并链接** | 按父节点判跨壳，链接放行、文本不放行 | 导航条 1 行 ✅，各区块互不串味 ✅ |

实测 `https://m.baidu.com/` 最终渲染（10 个 widget）：

    [输入框 440×40]

#### 3.3 其它平铺期规则

- **配色分层**：没有版面，只能靠颜色区分 —— 链接 `#6AB7FF`、标题白、正文 `#CCCCCC`
  （站点自带 `color` 优先）。
- **列表项**加 `"- "` 前缀（平铺后没有缩进也没有项目符号）。
- **按钮**在平铺下也走 label：`create_button` 造的是固定 70×35 的 lv_btn，
  中文两三个字就被切掉。
- **输入框**给满宽单行（440×40），不再用 CSS 的 240×32。

搜索框回来了：`[Browser] input: ph="输入关键词" val="" 440x40`。
之前"百度没有搜索框"是因为输入框被塞进零高度的容器里。

### 4. 平铺阶段暴露并修掉的两个真 bug

#### 4.1 `font_zh_16` 完全没有 ASCII

`tools/check_ascii_glyphs.py` 实测：`font_zh_16` 的 **0x20–0x7E 全缺 95 个**。
原因：当年 `fix_font_symbols.py` 只扫了**源码里的 CJK**，ASCII 从没验过。
LVGL 没配 fallback 链 → 网页里的数字、英文、@ % . / - 全是豆腐块。
`font_zh_24` 反而有 ASCII 但缺中文标点 —— 两边互补。

修复：`tools/fix_font_ascii.py` 按"必收集合"求差集追加
（16px 3785 → 3926 字，24px 996 → 1051 字），再 `gen_fonts.py` 重生成。

> 教训：**符号表必须同时覆盖 CJK 和 ASCII**，只扫一边必然漏。

#### 4.2 HTTP 不跟随 3xx 重定向

`http://www.baidu.com/` 返回 `302 → https://www.baidu.com/`，
旧代码 `if (status != 200) return RENDER_ERROR_NETWORK` —— 现象就是
"百度怎么直接网络错误了"。**不是网络问题，是没跟重定向。**

修复：`arduino_download_html()` 里解析 `Location:` 头，
301/302/303/307/308 递归重发（上限 5 跳），支持相对 Location 解析。

#### 4.3 WiFi 图标一开机就 LoadProhibited（LVGL 自带 bug）

把 WiFi 图标从 16 放大到 22 之后，开机 100% 必崩：

```
Guru Meditation Error: Core 1 panic'ed (LoadProhibited). EXCVADDR: 0x000004b4
lv_tlsf_free (lv_tlsf.c:1166) ← lv_mem_free ← lv_draw_mask_free_param
  (lv_draw_mask.c:217) ← lv_draw_sw_arc.c:168 ← lv_canvas_draw_arc
  ← drawWifi (icons.cpp:52) ← icon_wifi_set_level ← StatusBar_create ← App::begin
```

根因在**随包自带的 LVGL**：`lv_draw_sw_arc.c` 画**部分圆弧**的分支（line ~168）
无条件 `lv_draw_mask_free_param(&mask_in_param)`，而 `mask_in_param` 在这个分支里
**根本没初始化**；上面 full-ring 分支（line 121）是有 `if(mask_in_id != LV_MASK_ID_INV)`
保护的。栈上的垃圾被当成 mask type 去 free，直接炸。
放大图标只是把它从"偶尔"变成"每次都走到那条路径"。

修复两处：
1. `Lvgl/src/draw/sw/lv_draw_sw_arc.c` 补上 `if(mask_in_id != LV_MASK_ID_INV)` 守卫；
2. `src/app/icons.cpp` 的 `drawWifi()` 改用 `arc_polyline()`（14 段折线逼近圆弧 +
   `lv_canvas_draw_line`），**彻底不碰 `lv_draw_arc`**。

> 教训：改 vendored 库的源文件要记得，**改动在 `Libraries/Lvgl/` 下，不在 `.pio/libdeps`**
> —— 后者会被 PIO 覆盖回去。

### 5. 方案 C —— 服务端转码代理（Reader Mode）：**暂不做，知识留档**

> master 2026-09-23：写出来了不用它加载就没意义；只有专门做的站点才适配得了。
> 真要走的是 D（搜索优先 + 广告过滤）。本节保留，将来若要重开可直接照着做。

这是**唯一能在 ESP32-S3 上拿到"接近手机浏览器"体验**的路线，工程量反而比 A 小：

```
ESP32 ──HTTP──> 转码代理（局域网/公网小服务）
                  │  用 headless Chrome / Node + jsdom 跑真实排版
                  │  抽取正文 + 导航 + 链接（Readability 算法）
                  │  输出一份极简 HTML：只有 div/a/ul/li/p/h1-h3/input
                  └──> ESP32 用平铺渲染（现在的引擎完全够用）
```

好处：
- 本地引擎**永远不需要懂 CSS** —— 复杂活全在服务器上做完；
- 页面体积小（几十 KB），下载和解析都快；
- 可以顺便把图片转成低分辨率 / 直接去掉；
- 平铺模式下唯一要补的就是"链接可点"，代价很小。

风险：需要一台常驻服务器（家里 NAS / 云函数都行），离线不可用。
**先做平铺把浏览器救活，再评估要不要上代理。**

## 二、渲染裁剪：元素为什么莫名消失

> 原标题：**10. 浏览器渲染裁剪：为什么百度首页没有搜索框**，已并入本文

> 2026-09-23。症状：「屏幕上只有百度首页/设置/登录，搜索框都没有」。
> 本文记录**根因、取证方法、修复**，以及参考项目（babe32 / TactileBrowser）
> 的做法对比。以后再出现「页面上少东西」，先按 §2 的取证流程走，别猜。

---

### 1. 结论先说

**不是渲染器坏了，是布局树在 DOM→Layout 阶段就把搜索框吃了。**

百度首页的搜索框是这么包的：

```html
<span class="bg s_ipt_wr new-pmd quickdelete-wrap">&#xe610;
    <input id="kw" name="wd" class="s_ipt" maxlength="255" autocomplete="off">
</span>
```

外层 `<span>` 的文本内容是 **U+E610**——百度图标字体（icon font）的私有区码位，
在浏览器里显示成放大镜，在我们这儿没有任何字形。

而 `dom_renderer.cpp` 的 `build_layout_tree_from_dom()` 逻辑是：

```cpp
if (should_extract_text) {                    // span 在白名单里
    text = html_parser.get_element_text(element, &text_len);   // 返回 "\ue610"
    if (text && text_len > 0) { ... layout_node->text_content = ...; }
}
...
if (allow_children && (!should_extract_text || !text_content || text_content[0]=='\0'))
    ...遍历子节点...                            // ← 有文本就【不】遍历
```

`span` 属于 `should_extract_text` 白名单，`get_element_text()` 又把 `\ue610` 当成了
「这个元素有文本」→ **整棵子树不再递归** → `<input id="kw">` 从未进入布局树。

`m.baidu.com` 的搜索框外层是 `<div class="input-wrapper">`，`div` 不在白名单里，
所以它活得好好的。这就是「www 上没有、m 上有」的全部原因。

#### 1.1 数字对得上

串口日志：

```
[Browser] layout: viewport=1024 screen=464 scale=0.45 nodes=378 contentH=415->187
[Browser] widgets created: 105 (limit 150)
```

把抓下来的 HTML 用 Python 复现同样规则（`tools/html/anc2.py`）：

```
[被文本吞噬的 input]
  <span> text='\ue610' -> 吞掉 <input id=kw type=<none>>
      chain: ... < form#form < span.bg.s_ipt_wr.new-pmd.quickdelete-wrap < input#kw.s_ipt
```

**378 → 105 的缺口**主要就是这类「外层元素有文本 → 吞掉整棵子树」造成的，
不是 `MAX_WIDGETS` 撞顶（105 < 150）。

---

### 2. 取证流程（下次照抄）

不要靠肉眼看屏幕猜。三步：

1. **PC 上抓同源 HTML**（和固件用同一个 UA）：
   ```python
   UA='Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ... Chrome/120.0.0.0 Safari/537.36'
   urllib.request.Request(url, headers={'User-Agent':UA,'Accept-Language':'zh-CN,zh;q=0.9'})
   ```
   存到 `tools/html/`。注意**先 gzip 解码**再落盘。

2. **用 Python 复现我们的裁剪规则**，找出被吞掉的元素：
   `python tools/html/anc2.py tools/html/www_baidu.html`
   它模拟 `should_extract_text` 白名单 + `get_element_text()` 的递归拼接，
   打印「哪些 input/textarea 被父元素吞了」以及父链。

3. **对串口日志**：`nodes=` 是布局树节点数，`widgets=` 是真正建出来的控件数。
   两者差得多 → 裁剪规则有问题；`widgets` 撞到 `limit` → 才是数量限制。

#### 2.1 顺手量到的两个关键数字

| 页面 | HTML 体积 | 搜索框 | 说明 |
|------|-----------|--------|------|
| `https://www.baidu.com/` | **703 KB** | `<input id="kw">`（无 `type` 属性） | 桌面版面，设计宽 ~1024 |
| `https://m.baidu.com/`  | **188 KB** | `<input type="search" id="index-kw" placeholder="输入关键词">` | 移动版面，设计宽 ~375 |

m 版体积小 **3.7 倍**，而且自带 placeholder。**默认首页已经改成 m.baidu.com。**

---

### 3. 修复（三处，都在 `dom_renderer.cpp` / `layout_engine.cpp`）

#### 3.1 `subtree_has_form_control()` —— 不再吞掉表单控件

判定子树里有没有 `input(非 hidden)` / `textarea` / `select` / `button`，
有的话就**不**把本元素当纯文本叶子，继续递归。

```cpp
if (should_extract_text && elem_type != ELEMENT_INPUT_TEXT &&
    elem_type != ELEMENT_TEXTAREA && subtree_has_form_control(dom_node, 0)) {
  should_extract_text = false;    // 放开，让子树里的 input 能出来
}
```

深度上限 12，避免在大页面上退化成 O(n²)。

#### 3.2 `strip_icon_glyphs()` —— 删掉图标字体字符

就地过滤 UTF-8 字节序列（不用解码码点，够用且便宜）：

| 码位 | UTF-8 首字节 | 含义 |
|------|--------------|------|
| U+E000–U+EFFF | `EE 80..BF ..` | 私有区图标字体（百度 `\ue610`、淘宝等） |
| U+F000–U+F8FF | `EF 80..A3 ..` | 私有区图标字体 |
| U+FFFD | `EF BF BD` | 替换字符（解码失败） |
| U+FEFF | `EF BB BF` | BOM |
| U+200B–U+200F | `E2 80 8B..8F` | 零宽/方向控制 |
| U+00A0 | `C2 A0` | NBSP → 换成普通空格 |

**为什么不只是「好看」**：图标字符非空白，会让外层元素被判定为「有文本」，
从而触发 §1 的整棵子树丢弃。删掉它是修复的一部分，不是美化。

#### 3.3 自动视口 —— `<meta viewport>`

原来 `g_browserViewportW` 写死 1024。桌面站没错，移动站就惨了：
m.baidu 按 375 设计，用 1024 排版后整体压到 `464/1024 = 0.45`，
横向溢出、内容被压扁（`contentH` 只有 415）。

改成 **0 = 自动**：

```
<meta name="viewport" content="width=device-width,...">  →  用屏幕宽 464 排版
<meta name="viewport" content="width=640">               →  用 640
没有该 meta（桌面站）                                     →  回退 1024
```

串口 `vp <宽度>` 手动覆盖，`vp 0` 恢复自动。

配套：`layout_set_screen_width(CONTENT_W)` 由 `browser_screen.cpp` 在
`ensureEngineInit()` 里注册，供 `device-width` 取值。

#### 3.4 `MAX_WIDGETS` 150 → 200

修掉吞子树后节点能走到底，150 会在长页面撞顶。按 LVGL 池 128KB 推算，
200 个 ≈ 76KB（used ~78%），仍有约 28KB 余量。

### 4. 参考项目对比

#### 4.1 babe32（ESP32 文字浏览器）

- 走**代理**：`https://www.textise.net/showText.aspx?strURL=...`，先让别人把页面
  变成纯文本再解析。牺牲原站点，换极低的解析成本。
- **不建 DOM**，单遍 tokenizer，元素只有 `HEADING/PARAGRAPH/LINK/LINEBREAK`
  （表单是后来的 `html-forms.md` 计划补的）。
- 表单计划（`docs/plans/2026-03-13-html-forms.md`）值得抄的点：
  - `hidden` input **不渲染、只存值**（我们目前把 hidden 当 `ELEMENT_INPUT_TEXT`
    处理，靠 `type=hidden` 判断后 `return NULL`，行为一致）；
  - `<form>` 记 `action` + `method`，提交时 GET 拼 URL / POST 发 body；
  - submit 用**可点击 label**，不用 `lv_btn`（"renders as noise on this display"）。

- ⚠️ 它 `platformio.ini` 里 `board_build.flash_size = 16MB` +
  `partitions_16MB.csv`。**我们这块板不能抄**——bootloader 只认 8MB，
  分区越界会 `rst:0x3` 无限重启且无 panic。见 `docs/02 §1.4`、`docs/07`。

- 它和我们同款屏（480×480 ST7701S + GT911 0x5D），引脚定义完全一致，
  所以它的 **mbedTLS → PSRAM 重定向**思路能直接用（我们已经用了）。

#### 4.2 TactileBrowser（本引擎的上游）

- 目录：`参考项目/tactile-browser/TactileBrowser-main/`
- 结构：`html_parser` → `dom_renderer` → `layout_engine` → `lvgl_renderer`，
  和我们现在是同一套（我们就是在它基础上改的）。
- 上游没有 `strip_icon_glyphs`，也没有 `subtree_has_form_control`——
  **这个 bug 是上游就有的**，不是我们改出来的。
- 上游带 `tests/src/layout_render_tests.cpp`（桌面端单测）。我们要验证布局改动，
  最省事的办法是把布局引擎拉到桌面跑单测，而不是每改一次就烧一次板。

#### 4.3 QuickJS

- 目录：`参考项目/QuickJS-master`
- 定位是 **JS 引擎**，不是浏览器。现代站点（百度、淘宝）大量内容靠 JS 渲染，
  静态 HTML 里根本没有。要真正"渲染出来"得上 JS 引擎。
- 代价：QuickJS 编译进 ESP32 要几百 KB Flash + 运行时堆，且没有 DOM/BOM 实现，
  还得自己写 binding。**当前阶段不建议碰**，先把静态 HTML 的部分做对。
- 现实降级路径：**优先移动版站点**（m.baidu.com 这类），它们本身就是为
  "无 JS / 弱 JS" 环境准备的，静态 HTML 里就有完整内容。

1. **表单提交**：现在搜索框能显示、能输入，但没有 `<form>` 的 action/method，

## 三、UI 布局坐标与整页缩放

> 原标题：**浏览器 UI 布局与整页缩放**，已并入本文

屏幕 480×480。所有坐标以 `lv_obj_align(..., LV_ALIGN_TOP_LEFT, x, y)` 计。

### 1. 竖向分区

| 区间 | 内容 |
|---|---|
| 0–28 | 系统状态栏 `StatusBar_create(scr)`（电池+FPS / 时间 / WiFi+蓝牙） |
| 28–442 | 内容区 `g_content`，476 宽 / `CONTENT_H`=414 高，可上下滚动 |
| 444–480 | **底部控件行**（两组互斥，见 §2） |

- 加载遮罩 `g_loadingOverlay` 与内容区同尺寸同位置（2, 28）。
- 进度条是内容区顶部的 **4px 细条**（2, 28），进度文字在 (300, 34)。
  早期版本进度条放在 (10, 414) 会压住网页内容，已改。

### 2. 底部两组互斥工具栏

底栏只有一行（y=444，高 36），要放的按钮比一行能容纳的多，所以分成两组切换：

- **组 A（默认）**：`退出 / 网址 / 加载`
- **组 B**：`后退 / 前进 / 首页 / 加载 / 退出`

**切换按钮固定占 x=404**（就是原来「已加载」状态文字那一格），配色与其余底部按钮完全一致
（`0x1a1a1a` 底 / `#444444` 描边 / 6 圆角 / 白字 / `font_zh_16`）。两组切换时它**不挪窝**，
手指不会按空；标题随状态在 `更多 ↔ 返回` 之间变。

坐标核算（勿随意改，改了要重新核一遍是否重叠）：

```
组 A：退出 2–42 | 网址 46–346 | 加载 350–400 | 切换 404–478
组 B：容器 g_navBar 2–398，内部五个 76px 按钮 @ 0 / 80 / 160 / 240 / 320
```

#### 实现约束

- 可见性**统一走 `applyBarMode()` 这一个出口**。`switch_bar_cb` 只翻转 `g_navModeB` 再调它。
  不要在各处手搓 `lv_obj_add_flag(..., LV_OBJ_FLAG_HIDDEN)` —— 两组一旦不同步就再也切不回来。
- 组 B 用**手工排布**而非 flex：等宽可控，切换按钮的位置才稳。
- `g_status` **保留对象但加了 `LV_OBJ_FLAG_HIDDEN`**。
  `startFetch` / `tick` / `BrowserScreen_close` 里有几十处 `lv_label_set_text(g_status, ...)`，
  隐藏后照常调用、不影响逻辑。将来要恢复显示，删掉那一行 `lv_obj_add_flag` 即可。

#### 历史：不要再做右下角圆形 FAB 菜单

曾实现过一个 56px 圆形悬浮按钮 + 上方竖排菜单，**master 明确否掉**：他要的是底栏同配色
按钮整体切换这两组，不是浮在网页上的圆钮。相关代码（`g_fab`/`g_fabMenu`/`makeMenuBtn`）已全部删除。

> 教训：编辑被中断（429）后留下过半状态 —— `g_navBar/g_switchBtn` 已声明却没创建，
> 而 FAB 的声明被删、代码还在引用 → 文件**编译不过**。中断后先 Grep 残留引用再继续。

### 3. 整页缩放：viewport ↔ 屏幕宽度

网页按 `g_browserViewportW` 排版（默认 **1024**），渲染时整棵树等比压缩到内容区宽度 `CONTENT_W`=464：

```
scale = CONTENT_W / viewport
```

> 曾经的 bug：`layout_engine.cpp` 的 `s_layoutWidth` 只在 `layout_context_create()` 里赋值，
> 而该函数**全项目无调用点**（排版实际走 `dom_renderer_build_layout_only()`）→ `s_layoutWidth` 恒 0
> → `f` 恒为 1.0 → **整页缩放形同虚设**，页面按 464 挤排、只露左上角。
> 修复：新增 `layout_set_viewport_width()`，在 `dom_renderer.cpp` 的 `layout_calculate_dimensions`
> 之前调用。改这块前先确认这条链路还在。

#### 实测数据（百度首页，内容区高 414）

| 视口 | scale | 缩放后内容高 | 填充率 | 版面 |
|---|---|---|---|---|
| 1024（默认） | 0.45 | 187 | 45% | 保留桌面版面比例 |
| 650 | 0.71 | 295 | 71% | 偏窄屏流式 |

视口↓ → scale↑ → 内容更大更充满，代价是排版更接近手机窄屏、失去桌面多栏比例。
**默认值仍是 1024**（master 当初为保桌面版面定的），没有擅自改。

#### 怎么试

串口命令，无需改代码、无需重新编译：

```
vp 650                      # 设视口（下次加载生效）
browser https://www.baidu.com
```

看日志里的 `layout: viewport=... scale=... contentH=...->...` 判断效果。
`vp` 的范围被夹在 320–2048。

> ⚠️ 诊断打印 `render done. visible=414 scrollable=-402 total=12` 里的 `scrollable` 是
> `lv_obj_get_scroll_bottom()` 的返回值，内容比容器矮时是**负数**，不能当"内容总高"读。
> 判断内容高度看 `layout:` 那行的 `contentH=原始->缩放后`，别看这行。
